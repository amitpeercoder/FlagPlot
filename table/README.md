# The table

A prototype of the player's interface: a chart table seen from the commander's chair, drawn in the browser and played against a real game. It is a prototype, kept to find out what the interface should be; it is not a stage of step 3 and nothing depends on it. Decision 0154 has what it is and what it found.

It plays the game. It is not the umpire's: it is given one seat's tools and nothing else. It never reads a replay, a save, a batch file or the event log.

## Run it

From the top of the repository:

```
cargo build --release -p sim-cli
python3 table/serve.py
```

and open the address it prints, `http://127.0.0.1:8742/table/KEY/`. That is the new game screen (decision 0185, below): choose the scenario, the seat and who plays the other side, and begin.

A game can still be named on the command line, and the bridge then holds that game alone, as it did before the screen:

```
python3 table/serve.py data/scenarios/stage-3-proof/07b_slice.toml --seat allied --start 1942-08-07 --island "1=Guadalcanal@1" --island "2=Tulagi@4"
```

Then open http://127.0.0.1:8742/. That scenario is the 39 days of the staff's setup with the Japanese side's intents stated and the Allied side given nothing, so the Allied seat states its own.

`--start` is the date of day 1, for the clock. `--island` names an island the scenario has (its number, a name for the order form, and the number of a base on it), because no tool lists a scenario's islands yet. `--directives` is a file of directives from the commander above, as `table/directives/` has them (decision 0157); without it the table shows none. `--map` is the map file to draw (the default is the slice's); it is used for a game named on the command line, and at the new game screen before a game is begun. A game begun from the screen is drawn on the map its scenario names (see "The chart's coastline" and `scenarios.json`). `--port` is the port. The page loads its drawing library (three.js r128) and its fonts (Barlow Condensed, Courier Prime, Libre Caslon Text) from `table/vendor/`, which the bridge serves (`vendor.toml` there gives each file's source, SHA-256 and licence); it fetches nothing from another site.

## What is in it

- `serve.py`: the bridge. Started with no scenario it serves the new game screen and holds the game begun from it. Started with one, it starts `sim-cli mcp SCENARIO --seat SIDE`, passes the page's tool calls to it one at a time, and serves the page and the map's hexes; with `--watch`, a watched game (below). Python's standard library only. It listens on this machine alone.
- `scenarios.json`: the scenarios the new game screen offers, and the file for each game offered.
- `seat_mcp.py`: one seat's door as a Model Context Protocol server.
- `check_watch.py`: the check of a watched game by script. `check_screen.py`: the check of the new game screen and its games by script.

**The intelligence paper** (decision 0226). The Staff menu has Intelligence, which opens a sheet titled INTELLIGENCE SUMMARY: what the seat holds of the enemy, drawn from one call of the tool `intelligence` made when it is opened (not at load, not on a refresh) and from nothing else. The parts come in the order the answer's `parts` gives (SEEN, LOST SIGHT OF, CLAIMED, WHAT THE ENEMY HAS DONE, ASHORE, ENEMY BASES, ENEMY SUBMARINES, BEFORE THE GAME); a part the seat is not given (`not_kept`) says so under its heading; with no part it says one line of the staff's. Contacts, bases, our own units and places are links as on the cards. A lost contact's line opens how it was last reported, and SHOW ON CHART marks the last place of each with a cross. BEFORE THE GAME has one link to the directives and quotes none. The page parses no words, shows no points and no result, and a watched game reads the same call for the seat watched. `check_screen.py` checks it by the page's text, by its own functions run in node on an answer, and on the table's copy of scenario 128 (three days, the Allied seat) and the 39 days at the first evening.
- `index.html`: the page. One file, no build step.
- `directives/`: the directives a seat is given from the commander above, one file a seat of a scenario, written by hand in the game's own words. `guadalcanal_allied.json` is for the Allied seat of the 39 days: add `--directives table/directives/guadalcanal_allied.json` to the command above.

## What it does

- Wherever a force, a base, a ship, an air group, a land unit or a contact is named, in the report, the plan sheet or a card, the name is a link: it opens that thing's card and turns the chair toward it. The page's address ending `#see=task_force:1` does the same (decision 0158).
- "Read the report" at dusk is the staff's evening report, one sheet in place of the long return: where things stand, what happened since the last evening, what is for the commander's decision or notice, and what comes this week. A part with nothing to say is left out. It is made from the briefing's figures, the command state and the schedule; the full return is one step from it.
- "Read the plan" on an intent of the commander's opens the plan sheet: the intent, its risk and leave, and under it the staff's own intents as a tree, each with its plan and state, how it is going, what the staff decided for the coming day and why, what binds that decision and what would change it. A plan that waits can be approved there and a live one cancelled; the risk can be set and the intent withdrawn. A plan is changed by instruction, never line by line. The sheet is one tree: a line a task with a word for where it stands, and the staff's reasons one step down under each, in its WHY fold. Above the brief, from the tool `order` (decision 0159, rule E), the plan as the staff hands it in: its phases in order with the one under way marked, what it waits for with the day it is expected (in the enemy's colour while unmet), the men wanted and to hand, and the day it expects to be ashore; a refusal shows nothing. Under a take whose plan is preparing, one line says what must be known before it goes (decision 0159, 13), from the plan's `need_to_know`: what is asked and by what (the knowledge limit or the risk), what is held with its age and what it could be in truth, who is looking and since when, the carrier force moved to look and its hex where there is one (decision 0159, item 14), and whether it is met; it is in the enemy's colour while unmet. It sets no knowledge limit.
- When the game is over the page opens "How it ended", once, and the umpire's slip opens it again: who won and by what name (a minor, major or decisive victory, or a stalemate), then what each side did in two columns (enemy ships sunk and left out of action, aircraft destroyed, men lost, supply landed, days an airfield was open or shut, places held at the end), the scenario's note on the war itself where it has one, and the umpire's points one step down. In a watched game the result is read from the final briefing of the side watched, and a page loaded after the end reads it from the final briefing too. A game with no objectives says so.
- The order paper's force controls have a "Fuel" row (decision 0201), offered only where another force of the side has a ship whose class fuels others at sea (an oiler, as the force's ship lines say): tick it and choose the force to fuel from. It cannot be signed with a course, which ends the fuelling. The diary and the plot say, in the game's words, what each ship took, when fuelling was broken off and why an order ended.
- "Dry run" on the plan sheet, in a game that has a trial (decisions 0178 and 0181): the order is played through by the staff at the size chosen, plain, beside the side without the order, or at later dates the staff picks. While it runs the buttons are off and a line says how many runs of how many days are played and the seconds gone. The estimate opens as its own sheet, brief first: in how many runs the aim was met and held and by what day, what it may cost each side as lowest, middle and highest, and where the runs part; later dates are set in columns. What it needs, what was assumed of the enemy and the staff's own words are one step down. It says "runs" where the records say worlds. It changes nothing in the game. An order to the staff on the order paper has its own DRY RUN beside SIGN AND SEND: the draft is played and stays unsigned. Under "What if" on the plan sheet a change of risk, or "not before" a day, is previewed and played beside the plan as it stands, run for run, and can then be given from the estimate with one press; nothing is given until then.
- The pieces are period tiles: cream, in ink, leaning toward the chair. A rectangle is the side's own and a diamond the enemy's; a silhouette says what it is (a carrier, a surface force, transports, an escort, the crossed box for men ashore, a pennant for a base); a dashed frame says it is only reported, and such a tile fades as its report ages. The tiles grow as the commander sits back.
- A touch on the chart, when nothing is being drafted, shows what the side holds of the thing touched. Of the enemy: a contact with its age in pulses, or a place with the latest estimate of his men, where it came from and its age in days, and the words that it is a report and can be wrong. Of its own: a force (what it is doing, its ships and their fuel, the air groups and men aboard, whether the staff or the commander has it) or a base (its stock, days of supply, men ashore, air groups and the forces lying there). A touch on a tile is a touch on that thing, whatever else lies in its hex; a base or a place leads to the forces and contacts lying there. A contact's card says how it is known, from the report that last gave it. Which directives were received and read is remembered across a reload of the page.
- A land unit's card (decision 0216) says in whose hands the unit is and offers GIVE A DIRECT ORDER, which opens the order paper with: posture (defend, or attack with when spent: hold, fall back, left to supply), a march to one of the places the tool lists as joined by land, marked on the chart while chosen, or halt, and what it does on a quiet day (stand ready, train, work with a job or the staff's choice). It offers only what the engine would take, says the costs of a march or an attack before signing, and holds the unit first (at dusk), as a force's and an air group's orders do.
- One order paper gives every order (decision 0221, stage 3): to the staff, to a task force, to an air group or to a land unit. It opens at the right in the card's place, with a way back to the card it was opened from ("GIVE A DIRECT ORDER" on a card, or an order of "orders you can give" on a base, hex or force card), and has the same parts in the same places: TO (the staff, or the unit by name, linked); THE ORDER, with the controls the kind needs (a force's speed, readiness, course, fuel and ships; an air group's mission, search arc and base; a land unit's posture, march and doing; the staff's end and risk); IN WHOSE HANDS, for a unit, whose it is now and whose it will be once signed ("The staff's now. Yours once signed: you keep it out of the staff's plans."); ACTS, when it acts, before signing, in the words SIGNED uses after ("Acts at 1800, with tonight's orders" at dusk; inside a day "Acts at once", or "Acts at 1800, for the coming day" for an order that cannot act inside the day, decision 0219; a draft of both says which part is which); the staff's reading, shown open, with DRY RUN where the game has a trial; then SIGN AND SEND and TEAR UP.
- The paper stays open while the chart is touched, for a course's points (the course is set on the chart from the paper's own list) or a march's place; the chart draws what is drafted while the paper is open: a course, a search arc, the deny circle, the places a march may go to. A touch that picks nothing opens no card. Escape, or the way back, tears up a draft with nothing chosen, and asks in the paper where something is chosen. Signing closes the paper and the order is under SIGNED. A refusal keeps the paper open and says, line by line, what went and what did not ("Speed: sent." and "Course: NOT SENT" with the engine's reason); what was sent is not sent again on a second try; where nothing of a unit's order went, the hold sent before it at dusk is taken back (`take_back`), so the unit is not left held for nothing. An air group's mission and its search arc, signed together, are one entry under SIGNED, taken back together.
- The evening report says what came today and what comes tomorrow (decision 0215), and the fold of what stops the clock offers "reinforcements arriving", off until ticked. The day's plot shows an entry under the night of its day.
- The plan's paper is one tree, for a plan that waits and a plan in force alike: the order at the root, its tasks under it, each under its parent with the rule down its left; under a task the units it orders, each by name, linked, with what it is ordered, and one fold, WHY (what was weighed, what was chosen, what holds it back, what would change it). A plan that waits is read from `propose` (its tree, its hand-in orders and its arcs), a plan in force from `command_state` and `staff_orders`. A task's search arc is drawn on the chart while its fold is open or the task is under the pointer. Each plan's APPROVE and CANCEL are given once, under its line at the top; the staff's working in full is the last fold. The cautions of the staff's working (decision 0217) stand under their task in the warning ink. While a carrier's, a carrier force's or a base's card is open, the chart draws faintly what its air groups are set to do: a fan for a search, a ring for the greatest strike radius.
- "What is coming" (under STAFF) is the schedule: the air groups due and the forces not yet available, by date. With the directive it takes the place of the lists in the staff's return.
- Shows the directive from the commander above when one is due: the first on the first evening, a later one when its condition holds (a named base is the side's own). A new one opens by itself and stays on the desk. It carries no points; the staff's full return, which does, is one step away under its own name. The page's address ending `#directives=all` shows every directive, for reading the drafts.
- Draws the chart from the map's hexes, the side's forces as blocks, its bases, its men ashore, its contacts and its estimates of the enemy ashore. A contact and an estimate fade with age.
- An order to the staff: touch the chart at a base or at open water, or open a force's card for the waters it lies on, choose the end and the risk on the order paper, and read the staff's reading before signing. Signing approves that preview; a risk other than balanced is set after it. The reading is the plan's paper in short, drawn by the plan paper's own functions (`proposedTree`, `paperNode`) from `preview`'s `with_change.tree` and `would_hand_in`: one line at the head that says what would serve the order ("Task Force 17 would work these waters from <position> (q, r)."; "The staff would take it up in these tasks:"; "Nothing can serve this order yet." in the warning ink), then the tasks the staff would form with the units each would order, one line each, a WHY fold for each (closed), cautions in the warning ink, and what cannot be done said once as a fact under its task ("No air base can reach these waters: Port Moresby, in these waters, has no bomber or search aircraft the staff may use.") with what would change it in that task's WHY, and the staff's working in full as the last fold. The draft is "this order"; there are no counts and no numbers for tasks the player has not seen. Where a force or unit is not free because of another order, the reading names that order as the player knows it and links it to its paper (an order of his in force opens its plan's paper at that task, where WITHDRAW THIS ORDER is; one still signed goes to its entry under SIGNED, with TAKE BACK; a hold is the unit's own card, with RETURN IT TO THE STAFF); the same words and links are in the plan's paper and in a reason's WHY. The reading is worked at balanced risk, since `preview` takes one command and a risk is a `set_limit` on an order already in force; it says so only where the risk chosen is not balanced.
- "Next day" resolves a day. "Carry on" resolves days until something stops the clock (an interrupt fires, the game ends) or the player stops it. A day that has been resolved is then plotted pulse by pulse, the night, the morning, the afternoon and the end of the day: the forces move as the side's own events say they steamed in that pulse, and SINCE in the stop paper gives what the side was told in it, with the names of its units and places. The events come from the tool `events`.
- The clock shows the hour a commander commands at: a game day runs from 1800 to 1800, so the orders for day 1, whose daylight is the date given as `--start`, go in at 1800 the evening before.
- The stop paper (decision 0221), a column down the left, shows the clock; WHY THE CLOCK STOPPED, each reason with the staff's reasons ("Why") and a way to switch that standing interrupt off; FOR YOUR DECISION (a force asking leave, a plan that waits, a directive unread); SINCE, the reports since the clock last stopped; YOUR ORDERS, the orders in force, each opening its plan, with the line "Plans launch: when ready" or "on my word" and its switch; and SIGNED, every direct order and command signed and not yet acted on, read from the tool `queued`, each with when it acts and TAKE BACK (the tool `take_back`) while the clock is stopped. Each outcome is said where it belongs: a refusal as NOT SENT in what was signed, a stop under WHY, a prompt while a place is picked above the chart's controls, the second touch of New game and Restart in the GAME menu. Escape is one listener and answers the topmost thing: a place being picked, a paper for reading, a draft (an empty one goes back to its card), a card, a menu, the fold, the drawer. At a stop the focus goes to the first thing that waits, or to WHY; a closing card or paper gives the focus back to what opened it. While the clock runs SINCE says a count to a reader of the screen, not each line, and the clock's state is said once at each change. Ctrl+Enter signs the paper from anywhere in it. In a window under 1100 wide the column is a drawer, open at load and at every stop, its head showing a chevron and the count of what waits, and the two controls that run time always in sight under the head.

- An order's limits (decision 0222, step 4): the order paper has a part LIMITS, folded, between THE ORDER and ACTS, with a line for each limit something reads on that kind of order (the table in decision 0222, "As built: step 4, the table"): the forces by kind (the staff's choice, use only these by name, or none), from where they lie, supplied from, keep within (a circle of whole hexes round a place, moved on the chart), strike first and these waters first, protected ships, and for a take or an island not before, wait for, after and knowledge; each set back with BACK TO THE STAFF'S CHOICE. The staff's reading is the preview of the order with all its limits as one, and signing sends them together; SIGNED shows them in the order's line, and TAKE BACK takes them back whole. The page chooses no source of its own (decision 0228): an order given from a base's card is sent with no source unless the player sets one, and where the staff chose the base a hold or an island is supplied from (the tool's `supplied_from`), the plan's paper says "Supplied from: that base, our choice", with CHANGE. A plan's paper shows the limits of the order in force, each with CHANGE and BACK TO THE STAFF'S CHOICE, which open the order paper for that one limit with the staff's reading of it before signing; tasks say what the staff set on them and what they read from the order. A base's card of the side's own says its reserve, with CHANGE. A reason of the staff's that speaks of a limit ends its WHY with YOUR LIMITS, links to that limit on the order it is set on, read from the reason's own list of limits. THE ORDERS, opened from YOUR ORDERS, lists every order in force and signed with its state, its limits and its rank; orders in force are moved up and down (buttons, or Alt and the arrow keys) and the ranks signed together, one priority limit each, as one entry under SIGNED.

## Where a scenario lets a seat stop inside a day

A scenario with `orders_inside_a_day = true` (decision 0156) offers the tool `advance`, and the table then works a pulse at a time:

- "Next pulse" resolves one pulse and "Carry on" resolves pulses until the clock is stopped. Each pulse is plotted as it is fought, from the tool `events`.
- WHAT STOPS THE CLOCK, the fold at the foot of the stop paper (decision 0221, stage 4), chooses what stops it: the table's own ticks (a contact, an attack on mine, a ship lost, my strike away, men ashore, reinforcements arriving, each evening) and the staff's six standing interrupts, each a tick that can be cleared and set (`set_interrupt`; `command_state` says which are off). A staff tick changed inside a day says "from 1800". "Each evening" is off unless ticked, so Carry on runs to the next thing ticked. The table's ticks are kept in the browser for the game, keyed as the directives are, and forgotten by New game and Restart; WHY THE CLOCK STOPPED is kept the same way and dropped once the clock moves. The leave to launch is not in the fold: it is a line of YOUR ORDERS.
- At 0600 and 1200 the order paper takes an order to one of the side's task forces and to the air groups in its hex; an order that acts only at dusk is kept for 1800 and ACTS says so (decision 0219). The order is taken in at the start of the next pulse. IN WHOSE HANDS says, before it is signed, that the unit is the commander's once the order is signed; a held force shows under SIGNED and on its card as "Yours: you keep it out of the staff's plans", with "Return it to the staff".
- An intent stated at 0600 or 1200 is taken up by the staff at dusk, and the tools' answers say so.

In a scenario without the key the table resolves a day whole and then plots it, as before. To try it on the 39 days, copy `data/scenarios/stage-3-proof/07b_slice.toml` into a folder beside it and add `orders_inside_a_day = true` under its `name`.

## A watched game

The table can hold a game in which agents command and the person at the table only watches and holds the clock (decision 0182). An agent is whatever makes the calls at its seat's door: the bridge starts no model and holds no key of any model.

```
cargo build --release -p sim-cli
python3 table/serve.py data/scenarios/orders-inside-proof/05_eastern_solomons_on.toml --watch --seat allied --seat japanese --keep /tmp/watched
```

`--seat` names each side an agent plays; a side not named is the script's, so `--seat allied` alone is an agent against the engine. The bridge starts `sim-cli serve SCENARIO --watched` and prints:

- the watcher's table, `http://127.0.0.1:8742/watch/KEY/`, to open in the browser;
- one door for each agent's seat, `http://127.0.0.1:8742/seat/KEY`.

Each key is made new at every start. Give each agent its own door and nothing else.

With `--keep DIR` the saved game and the transcripts are written when the bridge leaves (Ctrl-C, or a signal to end). It also writes `journal.jsonl` there as the game goes: every seat's call and every step, in the order they were sent. A game killed outright before it could save is played again from it, to the same game: `sim-cli serve SCENARIO --watched --seat allied=player --seat japanese=player --save save.json --transcript transcript.jsonl < journal.jsonl` (with the seats the game had).

**An agent at a door, by HTTP:** `GET DOOR/tools` lists the seat's tools and the door's own `wait`; `GET DOOR/instructions` gives the words an agent is given on taking the seat; `POST DOOR/call` with `{"tool": .., "arguments": {..}}` makes a call, answered `{"ok": the answer}` or `{"refused": the words}`. A call of `end_day`, `run` or `advance` is the seat's word that it is ready, and is answered when the watcher's clock reaches the stop it asked for. The door holds a call open up to 50 seconds (`--hold`), then answers `{"waiting": true, ..}`; the seat then calls `wait` (no arguments), as often as it answers so, until the answer comes. While its call is held a seat makes no other call.

**An agent by the Model Context Protocol:** `python3 table/seat_mcp.py --url DOOR` serves one door on standard input and output, as `sim-cli mcp` serves a seat, so a model with tools takes the seat as it would `sim-cli mcp`. For Claude Code, an `.mcp.json` entry whose command is `python3` with those arguments.

**The watcher's table** shows one side at a time as its commander sees it, with a switch between the two sides where both are agents'. Nothing on it gives an order. The seat's slip under the stop paper's head says whether each agent is ready and until when, or that it is waited for, and lists the calls the agent watched has made since its last stop, with the words it gave as its reason. The clock is "Next pulse" (or "Next day", where the scenario has no orders inside a day), "Carry on" and "Stop". Carry on is the page's: it steps whenever every seat is ready, plots each step from what the side watched was told, and stops when that side is told of a thing ticked under the clock sign, when the game ends or when stopped. "Begin again" is refused while an agent has called its door in the last five minutes.

**Kept:** with `--keep DIR`, on leaving (Ctrl-C) the bridge closes the game, and `serve` writes the saved game, `DIR/save.json`, and the whole transcript, `DIR/transcript.jsonl`; the bridge then writes each seat's calls to `DIR/transcript_allied.jsonl` and `DIR/transcript_japanese.jsonl`. A game begun again is kept beside it as `save-2.json` and so on.

**What the keys are for.** Each door answers its own seat's calls and nothing else, and no door returns anything the watcher reads. The keys keep a program from calling a door not its own, or the watcher's, by mistake. They do not stop a program on this machine that sets out to cheat: it can read the bridge's printed lines, or the game's own files. Watch fair agents.

**The check.** `python3 table/check_watch.py` (ports 8760 to 8762, `--port` for others) plays two short watched games through the doors as scripted agents would, with the watcher stepping, checks `seat_mcp.py` over a door, then the player's table without `--watch`, and stops everything it started. It shortens the door's 50 seconds to 3. It needs `sim-cli` built in release.

## The new game screen

`python3 table/serve.py`, with no scenario (decision 0185), prints one address, `http://127.0.0.1:8742/table/KEY/`, with a key made new at every start. The screen and the table are both there. Options: `--port`, `--sim-cli`, `--map`, `--hold` (the doors' wait, 50 seconds), `--keep DIR` (each game is kept in `DIR/game-N` when it ends: the saved game, the transcript, the journal and, where seats were played through `serve`, a file of each seat's calls) and `--scenarios FILE` (the list, `table/scenarios.json` unless given). `--seat`, `--start`, `--island`, `--directives` and `--watch` name a game, and are refused without a scenario.

The screen asks three things: the scenario, from `table/scenarios.json`, with its dates and length and what each side is to do; the seat, Allied, Japanese or to watch; and who plays each other side, the engine or an agent. It says what the engine is for the choice made (a staff carrying out the orders the scenario gives that side, or forces following the scenario's orders as written), and for each seat an agent holds, how the agent takes it. "Begin" opens the game and the page becomes the table. On the table "New game", touched twice, ends the game in hand, whoever is at a seat, and returns to the screen. "Begin again" begins the same game anew, and is refused while an agent has called its door in the last five minutes.

**The list.** `table/scenarios.json` gives for each scenario its name, dates, length, lines, the date of day 1, the islands' names, each side's directives file where it has one, its map (`map`, a repository path: the chart drawn is that map's; an entry with none is on the slice's `data/map/south_pacific.csv`, and every entry names it today), and its pairings: who holds each side (`person`, `agent` or `engine`), what the engine is (`staff` or `script`) and the scenario file that makes it a game. A game is offered only where a file gives the engine's side orders or orders for its staff, and the sides played by a person or an agent nothing. Kept by hand: a scenario renamed or moved is changed there. It offers today:

| Scenario | Game | File |
| --- | --- | --- |
| The 39 days | Allied against the engine; watching an Allied agent against the engine | `stage-3-proof/07b_slice.toml` |
| The 39 days | Japanese against the engine; watching a Japanese agent against the engine | `stage-3-proof/07c_slice.toml` |
| The 39 days | A person against an agent, either side; watching two agents | `staff/07_full_slice.toml` |
| The Eastern Solomons | Allied against the engine; watching an Allied agent against the engine | `second-proof/05c_eastern_solomons.toml` |
| The Eastern Solomons | Japanese against the engine; watching a Japanese agent against the engine | `second-proof/05e_eastern_solomons.toml` |

The Eastern Solomons has no file in which neither side is given anything, so it offers no game of a person against an agent and none of two agents.

**Every battle that has boats has them** (decision 0225, the designer's answer: the table offers one game of each battle, and where the battle has boats that game has them; decision 0227 places them). The pairings of Midway, the Coral Sea, the Eastern Solomons over five days and the 39 days of Guadalcanal play the files in `data/scenarios/table-boats/`, made by `scripts/table-boats/make_files.py` from the table's copies in `table-hunger/`, which stay on disk, since tests and the copies' own checks read them, and are not offered. Midway has fifteen boats (fourteen American, from the arcs and the support line of Bates's disposition of 2 June, and I-168 at the atoll), the Coral Sea four (USS S-42; I-21, RO-33 and RO-34), the five days five (USS S-42; I-19, I-17, I-33 and RO-34) and the 39 days thirteen, most of which enter on the day of their row. Each side's directive ends its situation with one sentence naming the side's boats and where they are, and each game's lines name both sides' boats. Each side's staff has its navy's pattern (Allied off bases, Japanese on lines) and moves no boat unless its commander orders a patrol; a side the staff plays leaves its boats where they start. The submarines' figures are played as they stand, not yet set from the record, as the copies' notes say. The folder's `a` files, both sides given their orders, are kept for the decision's measure and are not offered. Every file the table plays states, for both sides, that the side's staff chooses its sources of supply (decision 0228, the scenario key `staff_chooses_supply_sources` in the side's table). The 39 days play the files in `data/scenarios/table-rear-bases/`, made by `scripts/table-rear-bases/make_files.py` from the 39-day files of `table-boats/` with decision 0224's rulings of Nov 23, 2026: the Japanese runs start at Rabaul (a named simplification) and Espiritu Santo starts with 2,120 t of supply (a placeholder). `check_screen.py` checks each game as it checks Midway.

**How the bridge holds each game.** A person against the engine: `sim-cli mcp` for his seat, as without the screen. A game watched: `sim-cli serve --watched`, as `--watch` has it. A person against an agent: `sim-cli serve --watched` with both seats played, and no watcher. The bridge steps the clock itself whenever both seats are ready. The person's calls are his seat's own; a call of time (Next pulse, One day, Carry on) is held until the clock reaches its stop, and once pressed it cannot be taken back. While it is held he may read, and is answered as the watcher would be from his own side; he may not preview, try a dry run or order. Of the other side he is told only whether its commander is at his seat and whether he is waited for. Every request of a watcher's is refused in this game.

**An agent's seat.** Each side has a door, `http://127.0.0.1:8742/seat/KEY`, whose address holds for as long as the bridge runs, so that a client is set up once. A door answers only while its side is an agent's in the game in hand; it says "not yet at its seat" on the table until its first request in that game. When a game ends, every call still held at a door is answered that the game has ended and a new one begun. The screen, and on the table the button "The agent's seat", give for each agent's seat, to copy: the `claude mcp add flag-plot-SIDE -- python3 /…/table/seat_mcp.py --url DOOR` line; the same as an entry of tool-server settings, for a client that reads them from a file when it starts; the door itself; and a brief (the side, its directive where it has one, to play to the end, and to read nothing but what the tools tell it). Beside them the person is told that a model at a keyboard stops of itself long before a campaign ends, that a model with a shell could read the scenario's file and asking it not to is the only guard, and that a call may wait about fifty seconds before it answers that it waits. The door's opening words say that the clock moves when both commanders have finished (or, in a game watched, that a watcher holds it), and that any call may be held, not only a call of time.

**What the keys are for.** The table's key and each door's keep a program from calling what is not its own by mistake. They are no guard against a program on this machine that sets out to cheat, and none against the person himself: he sets the agent up, so he has handled its door. In a game of a person against an agent nothing of the agent's side, its calls or its reasons is sent to the page, and nothing of the person's to the agent's door; the door is shown on the table only behind "The agent's seat". What `--keep` writes holds both seats' calls and is the umpire's, for after the game.

**The check.** `python3 table/check_screen.py` (ports 8780 to 8785, `--port` for others) starts the bridge with no scenario, reads the list, begins every game it offers and plays a day of each, plays a person against an agent through several days with both the page's calls and the agent's door made by script, checks that the sides are kept apart, that a held call is answered when a new game begins and that the door serves the new game, runs `seat_mcp.py` against a door, checks that Midway plays the copies with submarines, that each seat has its own boats and none of the other's, and that each side's directive names its boats, and then runs `check_watch.py` for the bridge started with a scenario. It shortens the doors' wait to 3 seconds and stops everything it started. It needs `sim-cli` built in release.

## Submarines (decision 0218, stage 3: the table's part)

The table shows a side's own boats, its reports of enemy boats and the waters it suspects them in, and gives the orders the agent interface gives (interface 48). It reads only what a seat is given: `list_forces` `submarines`, `list_contacts` `submarine_reports` and `suspected_waters`, `propose` and `preview` `stations`, and the side's own events. An enemy boat is never drawn: nothing of one is shown but a report and the suspected waters.

- **A boat of the player's own** is a piece of her own on the table (a hull on a rectangle tile, the side's blue, not a task force's silhouette) and a card: class, where (latitude and longitude with the hex in brackets, linked), her station, salvoes left, what she is doing (on station, on passage, going home), sound or damaged, how long she is held down, and in whose hands (the staff's under the order named, the player's, or free). The card's GIVE A DIRECT ORDER opens the one order paper, "Take station at", the station touched on the chart; it acts at 1800 and says so as every order that does ("Acts at 1800, with tonight's orders", or "for the coming day" inside a day). SIGNED lists it with TAKE BACK. KEEP THIS BOAT OUT OF THE STAFF'S PLANS and RETURN IT TO THE STAFF are a force's, through `hold` and `release` with `submarine`. A boat on the map and sound is offered the order; one going home, damaged, sunk or gone home is not (the engine would refuse it).
- **A report of a submarine** is a mark of its own on the chart, a dashed diamond with a small hull in the enemy's red, fainter as it ages (a ship contact's mark is a ring), with a tile and a card: where, the date it was made, its age, and HOW WE KNOW: "Reported after a salvo on <ship>" where the events say so, "Sighted from the air" where the report has a cause the side is not shown (the report cites a salvo or a search; a search is seen by neither side).
- **Suspected waters** are drawn faintly on the chart with no boat in them. A card, reached from a hex's card inside them or by stepping the pieces at their centre, says what is believed, round where, how far and the day told. They are in the situation in words as well, with the day as a date.
- **The patrol order**, "Patrol these waters with submarines", is among the orders a hex's card (and a force's, on its waters) offers, only where the side has a boat. The paper has the distance as a small whole-number control (1 to 6 hexes, with the miles it makes), labelled "Patrol these waters," as the deny order's choices are ("Deny these waters, within 80 miles"); the waters are drawn, and the stations the staff would give, each named, from `propose`'s and `preview`'s `stations`, while the order is drafted. Signed, it is a line of YOUR ORDERS and SIGNED that says the distance ("Patrol the waters within 2 hexes of <latitude and longitude> with submarines", "1 hex" for one), and in the plan's paper the tree shows each boat under it with her station.
- **A link to a card** (a boat's name in SINCE, a force, a base, a contact, a hex) goes through one function, `see()`; at a narrow width, where the stop paper is a drawer over the chart, it shuts the drawer so the card opened is in sight (it lay under the drawer, and the click seemed to do nothing).
- **The stops.** A submarine's attack on the side stops the clock by a stop of the table's own (decision 0218, rule 56; no interrupt of the engine): "We are torpedoed: <ship>, by a submarine" where a hit follows the salvo in the same pulse, and "<ship> was fired on by a submarine at <place>" where none does. A boat of the side's own lost stops it with the ship lost: "Lost: <boat>". The fold WHAT STOPS THE CLOCK has the tick "a submarine attacks us", ticked at the start like an attack.
- **The war diary and SINCE** say the new events: a boat on the map or on station, fired, hunted, attacked from the air, left for home, reached home, sunk; an attack from a submarine on one of ours; a report of a submarine and its dropping; waters told; a claim from a submarine. A boat's steaming and being ordered to her station are routine and folded.

The first game for play with boats on the map is Midway (above).

`table/check_screen.py` and `table/check_watch.py` check each part. The games they use are `data/scenarios/table-submarines/` (scenarios 128 and 129 with their paths one folder deeper, three days, the seed that has the boat fire and be hunted on the first morning, the waters the Allied side is told of, and no patrol order for the player to give himself): placeholders, not for play, and not in `scenarios.json`.

## What it does not do

- It reads the clock from the words of a refused briefing when it is opened at 0600 or 1200, since no tool tells a seat the hour.
- It gives no order to a ship.
- A seat's orders kept for 1800 (decision 0219) are listed among what is signed from the page's own memory: a reload forgets the list, though the game still holds the orders, since no tool lists a seat's queued orders.
- It has no check in CI and no test.

## The chart's coastline

The chart is drawn from the map the game is played on, in that map's own frame (decision 0199). The bridge serves four things of it: `/map` (the hexes), `/frame`, `/coast` and `/names`. For a game begun from the new game screen they are those of the map of its scenario's entry in `scenarios.json` (loaded when the game opens, once for each map); for a game named on the command line, those of `--map`.

**The frame.** A map generated by the map tool says where it is on the earth in its header: the lines "Projection: hex (0,0) is centred at ...", "east_nm = (lon - ...) * 60 * FACTOR" and "Extent: every hex whose centre lies from ... to ... and from ... to ...". The bridge reads those lines (`read_frame` in `serve.py`) and serves `{centre_lat, centre_lon, factor, west, east}` at `/frame`, every longitude in the map's run: a map that crosses the date line (the Midway map's extent runs 163 E to 166 W) gives longitudes above 180, 163 to 194. A map with no such lines, as the hand-written placeholder maps have none, has no frame (`/frame` answers `null`) and the page draws it as it always did. The page draws longitude scaled by the frame's factor, so a hex is not stretched, letters the meridians and the position readout east or west (a longitude in the run above 180 is shown as 360 less it, west), and brings the hexes' and the names' longitudes into the run before drawing. The slice's chart is drawn 2 in 100 narrower than before, as the plan says, since it too is drawn true.

**The coast and the names.** Each map has its own, found by the map file's name in `table/chart/`: `<name>_coast.json` and `<name>_names.json` for `data/map/<name>.csv`. They are for the eye only: the game plays on the hexes and nothing in the simulation, the staff or a seat's tools reads them. With no coast file the page shapes the land from the hexes themselves. A names file gives each name's position west negative, as `data/oob/place_positions.csv` has it, and the page brings it into the run; a coast file stores its longitudes in the run already, so the page does not wrap it.

**The slice's coast.** `table/chart/south_pacific_coast.json` is cut from Natural Earth's 1:10m land and minor islands (naturalearthdata.com, public domain), clipped to 142 to 175 degrees east and 26.5 degrees south to 2 degrees north and rounded to three decimals, by `table/chart/clip_coast.py` with no `--map`, which takes the two downloaded GeoJSON files and the output path.

**The Midway coast.** `table/chart/midway_coast.json` (38 rings, 263 points) was made from the same two files, as shapefiles, from the top of the repository:

```
python3 table/chart/clip_coast.py --map data/map/midway.csv references/natural-earth/ne_10m_land/ne_10m_land.shp,references/natural-earth/ne_10m_minor_islands/ne_10m_minor_islands.shp table/chart/midway_coast.json
```

With `--map` the script reads the frame from that map's header, clips to its extent padded by 3 degrees on every side, brings each ring lying wholly west of the frame's western edge into the run (360 added to every point of it), and writes a ring that both files hold once. It reads GeoJSON or `.shp` (outer rings only; the clockwise parts of a shapefile). Standard library only. `midway_names.json` lists the five places with a row of `data/oob/place_positions.csv`, each at that row's position; no sea is named. Natural Earth's files are not kept in the repository.
- Words, stage 4 (decision 0221, rules 14 to 16 and 22 to 23): a held unit is "Yours: you keep it out of the staff's plans" everywhere and is "returned to the staff"; a signed entry is "taken back", an order to the staff "withdrawn", a draft "torn up". No caption explains a rule: the notes under each end of an order to the staff, the dry run's foot and its sheet lines are gone. The situation is a paper of its sections, each line through the table's words. SINCE, the diary and the report say an aircraft type short and a position with its hex in brackets, linked; in one task's WHY a place said in full once is "there" after. The prompt while a place is picked lies at the chart's top centre (under the head and its strip in the drawer layout). A failed read after a signing or a taking back says "Could not read what is signed" with READ AGAIN where SIGNED is. A firing of the staff's states its units by name and, where it has reasons, opens them from WHY.

## The second door: the browser's build (decision 0229, stage 4)

The page asks the game through one function, `reach(path, body)`. Under the bridge it is HTTP, as above. The page has one marked line before its script, `<!--@door-->`, which is a comment under the bridge; `scripts/web/build.sh` writes the site's page as this file with that one line made the script tag of `web/door.js`, which answers each path the bridge answers for a person against the engine: the game from a worker holding the game as WebAssembly, the list, the chart of each map and the seat's directives from static files made at build. The site, `target/web/site/`, plays a person against the engine in the scenarios the table offers, from any static host or a folder served on one's own machine, with no bridge and no network:

```
sh scripts/web/build.sh
python3 -m http.server -d target/web/site 8950 --bind 127.0.0.1
```

A game lives as long as the page: a reload begins it again from its first evening, as kept games are the next stage. Watching a game, playing against an agent and `seat_mcp.py` stay with the bridge; the new game screen offers only what the door offers. The page and `door.js` never name the module or its data, and `web/check.mjs` holds that on the shipped files.
