# Replay viewer

A page that draws the map and replays a finished run on it, pulse by pulse, with the events of each step and the chain of orders and events behind any one of them.

**What it is.** An umpire's debugging tool for the designer and developers, like the command-line runner. It shows the truth, and optionally each side's contacts beside it.

**What it is not.** It is read-only: it takes no orders and cannot change a run. It is not the game's interface, and nothing that plays the game may use it. See [docs/decisions/0018-replay-viewer.md](../docs/decisions/0018-replay-viewer.md).

It is one file (`index.html`), no build step, no outside dependencies, and it works offline.

## Make a replay

From the repo root:

```
cargo run -p sim-cli -- export data/scenarios/04a_night_action.toml --out viewer/replays/04a_night_action.json
```

Add `--seed N` for another seed, and `--labels data/map/south_pacific_anchors.csv` for the real map with place names.

`viewer/replays/` is git-ignored.

**The map's frame (decision 0199).** A replay of a generated map has `map.frame`: `centre_lat`, `centre_lon` (where hex (0,0) is centred), `factor` (the map's factor for longitude, the cosine of the centre's latitude) and `west` and `east` (the longitudes of its edges), all numbers and all longitudes in the map's run: a map that crosses the date line gives longitudes above 180 (the Midway map's are 163 to 194). The viewer places a place name in the hex nearest to it by `factor`, with the label's and the hexes' longitudes both brought into the run (360 added west of `west` where `east` is above 180), and gives a hex's longitude as east or west. A replay with no `map.frame` (a placeholder map, or a file made before it) is placed by the cosine of 12 degrees as before. `check.js` recomputes the nearest hex with the replay's own factor and fails a version 6 replay of a real map that has no frame.

## Open it

- Open `viewer/index.html` in a browser (straight from disk is fine), then pick a replay file with the button, or drop it on the page.
- Or serve the repo and name the replay in the address:

  ```
  python3 -m http.server 8765 --directory .
  ```

  then open `http://localhost:8765/viewer/?replay=replays/04a_night_action.json`. If the fetch fails the page says so and the file picker still works.

**View.** The View selector shows the Umpire's truth (as before), or one side's page: its own units exactly, the enemy only as the contacts that side holds, and only the events the engine let that side see (`SideView::events()`, decision 0047), numbered by the side. The export writes them in `side_views` (replay version 2, decision 0053); a version 1 file opens in the Umpire view only.

**Replay version 3** adds a top-level `aircraft_types` (id, name, `strike_radius_nm`, `extended_reach_nm`, `search_range_nm`) and an `aircraft_type_id` on every air group record, for the reach rings. A side's page carries the types of its own groups only. Version 1 and 2 files still open, without rings.

**Replay version 4** adds a top-level `steps`: the state at the end of every step, for every day and every phase whether or not the phase has events. The steps are the ones the page makes of the events (`start`, then for each day `orders`, `night`, `morning`, `afternoon`, `end`), and the export records each at its moment of the day (`crates/sim-cli/src/export/steps.rs` says which). An entry is `{ day, phase, changed, removed }`. The first entry (day 0, `start`) carries every record of the start state in `changed`; each later one carries only the records whose JSON differs from the same record in the entry before (same kind and id; a contact by its id, a ground estimate by its hex, for each side), and in `removed` the ids of records that are gone. The records are those of `final` (task forces, ships, air groups, bases, land units, each side's contacts and ground estimates), made by the same code, so the steps applied in order end exactly at `final`; claims are in `final` only. Kinds with nothing to say are left out, so a step that changed nothing is just its day and phase. The page takes each step's state from `steps` and works none of it out again. It still draws a step's own events from the events (the moves, fights, searches and the air layer, and the hexes a force steamed through), and takes from the events what a side's records cannot give: the holder of a base the side lost, a ship the side saw sunk, an enemy base a report found, and the base a base strike is on. A side's page cuts every entry to its own task forces, ships, air groups, bases and land units and its own side's contacts and estimates, as it cuts `initial` and `final`; each of its steps shows the state at the end of the umpire's step its last event is in. A step with no entry in `steps` is an error the page reports. A version 1, 2 or 3 file has no `steps` and is rebuilt from its events as it always was (where this page says the page rebuilds from the events, it is about those files).

**Command state** (decision 0107, stage 1 of step 3) is written beside the records, only for a side whose command state is not empty (nothing was ever set), so a replay of a run with no command is byte for byte what it was and the version stays 4. `final.commands` is `{ allied?, japanese? }`, each side's state being `{ intents, leaves, plans, commitments, next_plan }`: an intent is `{ id, kind: "keep_supplied", base, floor_days, interval_days?, set_day, plan, withdrawn_day?, limits }` (`limits` is `{ forces?: { ships, task_forces, source }, area?: [[q, r]...], priority?, protected?, risk, not_before?, wait_for?: { task_force? , land_unit? }, after?, targets?: { kinds, waters_first } }`, each limit left out when not set; the three after `risk` since decision 0159, rule C, and `targets` since decision 0190, and not drawn by the Command tab); `leaves` is `{ prepare, launch }`; a plan is `{ id, intent, state, baseline?, amendments?, runs? }` (state is draft, preparing, released, complete, failed or cancelled; `baseline` is `{ day, kind, ..., limits }` taken at the first approval; an amendment is `{ number, day, change }` with `change` holding an `intent` or a `limit`; a run is `{ number, ships, load_t, source, days: { load, sail, arrive, free } }`); a commitment is `{ ship, plan, run?, from_day, to_day }`. A weight is a JSON number from its millionths, as everywhere. Every entry of `steps` may carry the same `commands` (`{ allied?, japanese? }`): a side's whole command state at the end of that step, written in the first step where the state is not empty and again in each step where it differs from the one before, so the last entry written equals `final.commands`. The Command tab (below) draws it, and `check.js` checks it against `final.commands`. A side's page is given its own side's state only (`sideSteps` and `sideReplay` cut it, as they cut the records).

**Command.** The Command tab, beside the Events tab, shows each side's intents and what the staff did under each, for the step the viewer is on (the Umpire's page shows both sides, one under the other; a side's page only its own). It is built from `commands` in the steps and from the staff's `staff_reason` events; the export was not changed, and a replay without command state (an older file, or a run in which no intent was set) says so.

- **By intent.** Roots at the left, each sub-intent under its parent. A node shows its number, its maker (commander or staff), its statement in words, the level it is addressed to (the area, a base, a task force), its plan and the plan's state, the day it was set (and, greyed and struck through, the day it was withdrawn), and the limits that bind it read up the tree (risk, priority, forces, area, protected ships), with the intent that set one where it is not its own. A node appears on the step its intent was set or formed and stays.
- **Orders.** Under a node, the orders it issued, from the staff's reasons: by day, newest first, the step's day open and earlier days collapsed with a count. A line is the unit, what was ordered and the level that decided. A line that says the staff gave no order that day opens to its reason.
- **Click an order** to select its event (the Events tab and the Why pane show it), light its unit on the map (a task force, or the base or force an air group is with), and see its reason in the lower pane: what it serves with its chain up to the commander's intent, the evidence, what bound it, the working and what would change it. **Click a node** to show only the events that serve that intent (its commands, reasons, orders, notices and plan changes), across every step; click it again, the banner or Escape to clear.
- **Names.** An order line reads "order 55 · VMF-223 (air_group:10) · air mission: rest · decided at Henderson Field (base:1)": the name first, the id after it. A node says "hold Henderson Field (base:1)"; hover its words for the engine's own statement, which the reason pane also gives under Serves.
- **The split.** With the Command tab open the upper pane has most of the right column and the details pane about a third, which collapses to its header ("Details") when nothing is selected and opens when an order or event is. Drag the line between them (or focus it and press Up or Down) to change the height, or click the Details header to open or close it; a choice holds until the selection changes. The Events tab keeps its own layout until its line is dragged.
- **By level** regroups the same nodes by the level they are addressed to (the area, each base, each task force) and adds the leaves: the units that received orders, and what each was told by which intent.

`check.js` builds the tree at every step of each replay with command state and checks that at the last step it holds exactly the intents of `final.commands` (parents, makers, addressees, plan states, withdrawals), that no intent or order vanishes from one step to the next and none appears before its event, that every order shown under a node is a staff order of that side whose reason serves that node, that every reason's chain is the intent's path to its root and ends at an intent the commander made, that the events that serve an intent include its reasons and belong to its side, that a side's page holds no intent, order, reason or event of the other side, that a withdrawn intent stays in the tree with its day, and that a version 3 file and a version 4 file with no `commands` still open without a Command view.

**Air.** The map shows air activity from the events the replay already records, nothing else. The Air box in the map controls shows or hides the whole layer (it is off for a replay with no air events).

- A search arc as before (`search_flown`). A small filled diamond, in the searching side's colour, where a search's report put a contact (`report_received` caused by a `search_attempt`). In the Umpire view only: a faint line from the diamond to where the force truly was, and a grey ring where a search missed the force it looked for (`search_attempt` with `sighted` false, at that force's position at that moment). A side's page has the diamonds only: the engine gives it neither the miss nor the true place.
- A raid is the strikes launched in one step from one place (a ship or a base) at one hex, as the rules group them. Its line runs from the hex the group launched from (the group's base, or its ship's force, at that moment) to the hex the strike was sent to (`strike_launched`, `base_strike_launched`), labelled with its aircraft and escorts (`escorts_sent`). Solid with an arrowhead: it attacked. Dashed ending in a hollow ring: `strike_found_nothing`; in the Umpire view a grey dashed line and "target truly here" show where the force its report was about really was, found by following the launch to its report to the sighting or attack behind it (or "not traceable"). Dotted: no bomber got through. A raid on a base ends in a small square.
- A tally box beside each target hex gathers the fight there in one step: raids, aircraft, escorts, the patrol that engaged (Umpire only), shots, anti-aircraft fire, aircraft lost by side and by cause, ditched, landed elsewhere, lost with a ship, hits, ships sunk, and claims (written "claimed", which is what the claimant believes). A side's page says only what its own events carry: its losses without their cause, its attack without its hits. Zoomed out the box is a badge with the raid count; hover for the box. Click it: the event list shows only the events of that air fight (with a "show all" bar; Escape also clears it), and the raid's first attack (else its found-nothing, else its first launch) is selected, so Why and Led to show the chain of causes.
- Reach on request: select a force or ship, or click a base on the map, and the detail panel lists its air groups (type, mission, reach as at this step). Click a group to draw rings round its position: its strike radius, its extended reach (solid when the group is on extended reach, faint when not) and its search range, labelled in miles. A replay with no aircraft figures (version 1 or 2) says so and draws no rings.

Keys: Left and Right step, Space plays and pauses, Escape clears the selection.

**Measure.** The Measure button on the map turns on a mode in which two clicks pick two hexes. The readout gives the air distance (the engine's `Hex::air_distance_nm`, decision 0040) and the sea route in miles and hexes (the engine's `Map::sea_path`, decision 0017), or "no sea route"; the route is drawn on the map. Escape or the button leaves the mode. The page repeats both functions in whole numbers, and `check.js` runs them on `viewer/measure_fixture.json`, which the engine writes (`FLAGPILOT_UPDATE_GOLDEN=1 cargo test -p sim-cli measure_fixture` rewrites it), so the page cannot disagree with the engine.

**Replay version 5** adds three things to each base record, in `bases` of every step, `final` and a side's page (own bases only): `ammunition` (tons, left out when 0), `airfield_closed` (true when the airfield's damage is at or above `airfield_landing_refused_at`, so that it takes no aircraft; left out when false) and `days_of_supply` (the holder's days of supply in the base's hex at that step, worked by the engine's `SideView::days_of_supply`; left out where there is no figure, and in `initial`). Nothing else changed; version 4 files open as before, with a base panel that has no stocks.

**Replay version 6** (decision 0138, item 6) adds the pictures of the commands and the reports they sent, for a scenario run with command levels on; a scenario with them off exports as it did, byte for byte, but for the version, and has none of this. `final.pictures` is `{ allied, japanese }`, each a list of `{ command, contacts }`, one for each command of the side at the end (`area`, `task_force:N`, `base:N`, in that order); a contact is `{ id, hex, ship_count, kind, age_pulses, report_event, own }`, the numbers being that picture's own, `report_event` the event of the report that last made or refreshed it there, and `own` true where the command saw it itself and false where it was told. Each entry of `steps` may carry `changed.pictures` (`{ allied?, japanese? }`, a command's whole picture where it differs from the step before's or is new: the first step has every command) and `removed.pictures` (the words of commands gone), so the steps applied in order end at `final.pictures`. A `report_sent` event's `data` is `{ side, sender, report, listeners }`: `report` is the event number of the report passed (for "nothing there", the strike's own event), and each listener is `{ command, direction, arrival, day?, pulse? }` with the direction `up`, `sideways` or `down`, the arrival `on_time`, `late` (a pulse late) or `never`, and, unless never, the day and pulse it arrives, worked out by the export (a late report sent in the afternoon arrives in the next day's night). A side's page holds none of it: a command's picture is the umpire's.

**View: a command's picture.** For a version 6 file with pictures, the View selector has a Command picture list beside the Umpire and the two sides, one entry for each command of each side ("Allied · task_force:2"). The map shows the truth, as in the Umpire's view, with that command's contacts drawn over it as a side's page draws its contacts: fainter when older, dashed where the command was told of it and solid where it saw it itself, with the hover and the legend saying so. Step through the run and the contacts follow that command's picture alone, so it can be seen beside the truth, pulse by pulse. The Show box gives way to it; choosing Umpire, Allied or Japanese again leaves it.

**Reports.** The Reports tab, beside Events and Command, appears for the Umpire's page of a file with reports sent. Each row is one passing: the event number of the sending, the day and pulse, the side, the command that sent it, the report (its event number, a button that selects that event and goes to its step), and each listener as a chip: direction, command, and the pulse it arrives (struck through when never, dashed when a pulse late). Rows from later steps than the one on screen are faint. With a command chosen in View, the rows that reached it (as a listener, on time or late) or that it sent are marked, and "only those that reached the chosen command" keeps just those.

`check.js` checks a version 6 file's pictures: the steps applied in order end at `final.pictures`, the first step has every command, each command is one of its side (a task force or base the side ever had) and each contact of a picture is well formed and rests on a report of that side, and the model draws the pictures the file holds; every `report_sent` names a sender and listeners that are commands of its side, a report that is an event, a direction and an arrival from the lists above, and a day and pulse the way the rules count them; a side's page holds no picture; and a version 5 file (the same without pictures) still opens, with no command picture to offer.

**Land units.** The Land box in the map controls shows or hides the land layer (off for a replay with no land units).

- A counter for each side's units at a hex, in the side's colour, a crossed rectangle (a force is a plain one with its TF number), with a count in a circle where there are several and the men beneath. Units aboard ships are not drawn: they are in their force's detail ("N men of ... aboard") and the checker accounts for each. Click a counter: the details pane lists each unit's name, men, posture or activity, supply (fed share at the last night's charge, and days of supply at its own base there), experience, fatigue, whether it is dug in (fieldworks) and its orders.
- A fight ashore in the step is ringed as a surface fight is, with a tag "fight ashore, N events" that lists the events of that hex when clicked (the list shows only them, with a "show all" bar). A unit that marched (dashed line), fell back (dotted) or surrendered in the step shows its movement from the events (`march_day`, `march_arrived`, `unit_fell_back`, `spent_unit_fell_back`).
- A side's page holds its own units exactly. The enemy appears only as that side's estimate (`ground_estimates`): a hollow dashed counter marked "~men". On the Umpire's page an estimate is drawn for the side chosen in "Show".
- An order to a land unit that is selected in the Command tab lights its counter.

**Bases.** Click a base (including one a landing formed): the details pane gives, for the step, who holds it, its port, supply, fuel and ammunition on hand with days of supply, the airfield (open, damaged by how much, or closed), defences, the air groups there (type, ready and damaged aircraft, pilots, mission, patrol share or search arc, fatigue), the ships in port in no force and the land units in its hex. A side's page shows an enemy base's name, place and holder and that side's estimate of the enemy ashore there, nothing else. A small red mark beside a base means its airfield is closed; an amber mark means less than a week of supply. Both are in the legend. A file older than version 4 has no records of a base at each step, and says so.

**Intents on the map.** Click a node in the Command tab (it also filters the events, as before): a deny intent outlines its waters (the hexes within its distance), a stand-at or carrier intent rings its station with a line from the force, a ready-a-landing intent rings its landing hex with a line from the force (decision 0141), a take-a-place intent rings the place (decision 0142), a neutralise or raid rings its target with a line from each tasked base, a hold, cover, strike-ships, search-waters or build-up intent rings its base, and a keep-supplied intent rings its base and its source, with a dotted route for each run in the state (the latest staff route order to a force that carried the run's ships, between the run's load and free days). The node says in words what is drawn. Clicking it again, the banner or Escape clears it.

**Staff notices.** A notice (cannot meet the intent, waits for leave, a run ended, a landing ready or late, a build-up met, a place taken) is flagged on its plan's root node ("notice: ..." and the engine's words under it), the Command tab's label counts the step's day's notices, and "Next notice" jumps to the next step with one. A `staff_notice` event may carry an optional `intent` (the `met` notice of a take_place, "intent:N is met"); the viewer reads the notice by its `plan` and shows the engine's words, so it needs no change for it. A staff's `keep_supplied` under a hold, and a hold on an enemy base, are drawn as any other intent of that kind. A `bombard` intent (decision 0146) is read as "bombard base:N with task_force:M", is addressed to the task force, and is drawn as a raid is: its target ringed and a line from the force.

`check.js` also checks, at every step of each replay and in both side models, that every land unit in the state is drawn at its hex or accounted as aboard a ship (or gone, with no men), that the counters at the last step are `final`'s land units ashore and the estimates drawn are `final`'s, that the base panel's figures, trouble marks, air groups and ships in port at the last step equal `final`, that each intent's drawing is what it means (a deny outline has exactly the hexes of the map within its distance), that every notice is flagged on the node of its plan at its step and the counts and jumps are right, that a side's page holds no enemy land unit, base stock or intent, and that older files still open.

## Check it

```
node viewer/check.js viewer/replays/*.json
```

It syntax-checks both script blocks of `index.html`, runs the page's own pure functions on each replay (geometry, steps, rebuild against the final state, causes, labels); for a version 4 file it also checks that the entries of `steps`, applied from the first, end exactly at `final`'s records, that every step the page shows has its state, that a side's page holds nothing of the enemy's, and that the state taken from `steps` is the state the rebuild from the events makes, step by step (the one exception is the march a falling back gives a unit, which the rebuild does not make), the measuring functions against the engine's fixture, and on some synthetic edge cases and bad files. For the air layer it checks, in the Umpire model and both side models, that every launch has a launch hex that gives the engine's distance, that no strike or search is beyond its type's reach, that every raid's events are in its step and in one raid only, and that a side's page holds no true hex and no miss; a hand-built replay has one strike that found nothing, with its raid, tally and true hex asserted exactly. `node viewer/check.js --against-rebuild viewer/replays/*.json` also compares, for each version 4 file, the model taken from `steps` with the one the rebuild from the events makes, step by step, while versions 1 to 3's rebuild still knows every event. It exits non-zero if anything fails. No npm packages.

## Shells, bombs and the estimate of the enemy ashore (decision 0092)

The event list shows a shore bombardment (`bombardment_fire`, `shore_bombardment`, a claim with `from_bombardment`), men lost to fire (`men_lost_to_fire`), a ground report (`ground_report_received`), a report that a hex is empty (`ground_found_empty`) and a base a report found (`base_found`) as any event, in the engine's words; the map does not draw a bombardment. A base's side sees `shore_bombardment` without its `task_force`, and the firing side sees it without its hits. In a version 1 to 3 file the viewer rebuilds each unit's men from `men_lost_to_fire`, and each side's estimates from `ground_report_received` and `ground_found_empty`, and `check.js` compares them with `final.ground_estimates` (left out of a replay where no side holds an estimate); a raid's `hits_on_men` is written only when a hit landed on men.

## Cover and fieldworks (decision 0106)

The final state's land units carry `fieldworks`, the fieldworks a unit has dug, 0 to the ground figure `fieldworks_limit`, left out when 0 so that a replay made where nobody digs is as it was. In a version 1 to 3 file the viewer rebuilds each unit's fieldworks from the `fieldworks_changed` events (`dug`, `worn` or `lost`, with the fieldworks afterwards), and for a unit made by division from its parent's at `unit_divided`; `check.js` compares the rebuilt value with the final state's, as it does the men, the posture and the fatigue. A fatigue change `strained` is rebuilt like any other change of fatigue. `defences_worn` (a base's defences worn by fire) is shown in the event list in the engine's words and is not rebuilt. A side's page has the events of its own units and bases only: the enemy's fieldworks and defences are not in it.

## Forces that arrive (decision 0195)

`initial.entering`, in the umpire's file only, lists what a scenario holds apart until its day: one entry for each task force (with its ships, air groups and land units aboard) and each land unit or air group at a base, in the order of the state. An entry is `{ unit, day, side, hex? | base?, waiting?, task_force?, ships?, air_groups?, land_units? }`: `unit` is `task_force:N`, `air_group:N` or `land_unit:N`, `day` the day the scenario names, `hex` (`{ q, r }`) the place a force enters and `base` the base a unit enters at, `waiting` true once its day has come and it waits for its base, and the rest are the same records the state gives (so a held ship is a ship record). Every key but `unit`, `day` and `side` is left out when empty, and `entering` itself when nothing is held, so every replay made before this is byte for byte what it was and the version stays 6. The steps and `final` hold what is on the map, so a unit held apart is in none of their records before it enters. A side's page is given its own side's entries only (`sideReplay`).

The events `force_entered` (`{ force, side, hex, base?, ships, air_groups, land_units }`), `unit_entered` (`{ unit, side, base, hex, men, aircraft }`) and `entry_waiting` (`{ unit, side, base, day, wait }`, `wait` being `not_the_sides_base` or `takes_no_aircraft`) are shown in the event list in the engine's words, and a refused order names `not_yet_entered` (`{ unit, day, waiting }`). A force that enters is not drawn before the step of its `force_entered` event, and is drawn from it at the hex of the event with its ships; a ship held apart is known by name before it enters and is in no force until then, and an air group held at a base is at none until it enters. In a file with no `steps` the rebuild from the events does the same. `check.js` checks every entry (a force enters at a hex and a unit at a base, its day is from 2, nothing is both on the map and held apart), that the event agrees with the entry in day, hex and ships, that a force is in no state before its event and in the state from it, that a side's page holds its own entries only and names none of the enemy's, and that the rebuild from the events agrees.
