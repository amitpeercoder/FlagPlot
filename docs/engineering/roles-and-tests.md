# Roles, delegation and tests

Who does what, how work is handed out and reviewed, and how scenario tests are written. Moved out of `CLAUDE.md` on Nov 12, 2026, word for word, to keep that file short. `CLAUDE.md` states each rule that fails silently in one line and points here for the rest and the reasons.

## Roles and delegation

| Role | Who | Owns |
| --- | --- | --- |
| Product manager | Amit | What the game is, the spec, every decision marked "needs review", approval of each scenario plan. Not data: see "Who settles data" |
| Manager (since Nov 23, 2026) | The main session, Opus | Sequencing, briefing and reading the developers' work, opening, reading and merging pull requests, the tables. `docs/engineering/running-the-project.md` says what it settles and what it sends to the architect |
| Architect | The most capable model, called by the manager for one job at a time | Settling data, the plan for each scenario, crate boundaries, the determinism and traceability rules, the hand calculation, decision records, the class of a change above housekeeping, the last reading of a pull request of class 2 or 3 |
| Team lead | The manager; for a large build, an Opus subagent | Turning an approved plan into tasks, briefing the developers, reviewing their work against the plan and this file, reporting back what was built, deferred and unclear |
| Developers | Sonnet subagents | Implementation tasks, tests, bulk reading and summarising of reference material, code search |

Rules:

- **Use the cheapest model that can do the job well.** Haiku is enough for plain lookups.
- **The hand calculation is written by the architect before any code is delegated.** Developers make the code match it. Nobody changes an expected number to make a test pass; a mismatch goes back to the architect.
- **The architect opens and merges pull requests without waiting for Amit,** who delegated both on Nov 11, 2026. A pull request is merged only after its CI check is green, and what was merged is reported to him. Nobody pushes to `main` directly.
- **The reviews a change needs follow from its class** (decision 0233, Nov 27, 2026; the table is in `docs/engineering/running-the-project.md`). Class 1, housekeeping, which changes nothing the game does or says: the manager alone. Class 2, a bounded change: a short record by the architect and his reading of the pull request. Class 3, a rule: the plan, its independent review, Amit's confirmation where it is marked "needs review", and the architect's reading. The manager may call a change class 1 by the test the decision gives; above that the architect classifies, and in doubt it is the higher class.
- **Nothing reaches a pull request unreviewed.** The team lead reviews the developers. For class 2 and 3 the architect reads the pull request before it is merged, every change to `sim-core` in it, and that the three checks ran.
- **Questions go up, not sideways.** If a brief or the spec is unclear, a developer or the team lead stops and asks. Only the product managers settle a spec question.
- **A subagent's summary is a lead, not a fact.** Check any claim a design choice will rest on against the source before using it.
- **Two developers never edit the same files at the same time.**
- **Small jobs skip the chain.** A change of a few lines is done by whoever is holding it. Its class is still its class: size does not make a change housekeeping.

## Tests

- Each scenario in the spec gets one file in `tests/` and one TOML file in `data/scenarios/`.
- A scenario test writes out its hand calculation in the file's doc comment, then asserts those numbers exactly. From decision 0233 on the doc comment is the one place the arithmetic is written: it cites each rule by its record and number, or by its section of `docs/rules/` once built, and does not restate it, and the record names the test file and holds no calculation.
- A chance worked by hand over several draws (at least one hit in n shots, a fight that never opens, a bomber that is never hit) is written cut to six decimal places, as the engine's fixed point cuts, never rounded: 0.95^20 = 0.358485922… is written 0.358485. Ruled by the coordinating architect on Nov 13, 2026, after the rulebook-only test (`docs/validation/closing-tests.md`, finding R6). Doc comments written before then that round such a chance are not edited (nobody changes an expected number, and none of them is asserted); that record lists them.
- Build scenarios in the spec's order. Each adds one subsystem, so a failure points at the newest code.
- Do not start the next scenario until the current one passes and has been reviewed.
- **A scenario for play** (`for_play = true` in its `[objectives]` table; decision 0187) may have a scoring of its own. A scenario of record keeps the scoring it has, never chosen or changed for balance. Three guards bind a scenario for play:
  - **The reason before the number.** Every objective and figure of its own scale is written in the scenario's decision record, with its reason in terms of the mission or the history, before a run made with it is read. A figure chosen after a run is seen must be one another objective of the game already has, used by a stated likeness, or one that follows from the mission by a stated rule. A figure with neither is not written, whatever the band says. Where the architect has seen a run before choosing, the record says so.
  - **A band, read on the sign of the margin.** Over 1,000 games of staff against staff on seeds 1 to 1,000, each side given the orders its mission implies, neither side is ahead in more than 650 (a side is ahead when the margin is on its side, by however little). Outside it, the next means is tried once, with its reason, and each change is recorded beside the run before it and the run after; after two changes that leave it outside the band it goes to the designer with the counts. The levels are not a means: they are set for the scenario's size with a reason, before a run is read. The band is read again when the scenario's file or a doctrine it uses changes. The band says the staffs' games are a contest; it does not say the scenario is fair between two people.
  - **Agents, not only staffs.** Before it is called balanced, four games between agents are played, with two models, each as the first side twice, and their margins are reported beside the staffs'. They set no figure; if they all go one way where the staffs' are in the band, the designer is told.
- **A supply line is given only to a rear base,** and the scenario's decision record says for each line why the enemy could not have cut it; where he could, the cargo comes in ships that enter by date (decision 0195; decision 0196).
- **A scenario for play is never the scenario of a proof or of a validation measure,** and a proof's scenario is never made for play. A version for play of a scenario of record is a file of its own. [0187]
- **The hand-calculation tests run on the frozen step 1 figures,** `data/reference/step1`, for the length of step 2 (`docs/step2-spec.md`, "Tests while figures move"). A scenario test loads its scenario through `tests/common` (`common::load`, `common::from_text`, and `common::altered_reference` for a variant with a figure changed), and the agent's and the runner's tests through `LoadOptions::frozen_step1`, so the directory is named once, as `sim_data::FROZEN_REFERENCE_DIR`. A test never rewrites a scenario's text to point at another figures file. What passes there proves the rules compute what the hand calculation says, on known figures; it says nothing about the figures in use. A rule that adds a figure adds it to the frozen file too, with its first value (`crates/sim-data/tests/frozen_figures.rs` fails if it does not). The run baselines (`crates/sim-cli/tests/run_baseline`, and their day hashes in `tests/golden/pinned_hashes.txt` once decision 0233, C, is built: a baseline then changes only when a game does), `batch` and the recorded games follow the live figures and are remade with each tuning round; so do the tests that compare a run with a baseline, and the determinism scenario's and the soak's checks that a run repeats, completes and holds its invariants, so that tuned figures are held to them.
