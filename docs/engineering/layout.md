# Layout and crate boundaries

Where things are in the repository and which crate may depend on which. Moved out of `CLAUDE.md` on Nov 12, 2026, word for word, to keep that file short. `CLAUDE.md` states each rule that fails silently in one line and points here for the rest and the reasons.

| Path | Contents |
| --- | --- |
| `crates/sim-core` | State, rules, resolution, event log. No dependencies. No file or network access |
| `crates/sim-data` | Loads reference data, maps and scenarios from files into `sim-core` types. Every reader takes its text from a `Source` (`src/source.rs`, decision 0229, rulings 8 and 9): the disk, which every `load` function uses and goes on using (`load_x(path)` is `load_x_from(&Disk, path)`); a `Pack`, a set of files held in memory by the paths they were asked for, which `Scenario::load_via` reads a scenario and the files it names from; and `Noting`, which reads through another source and keeps every file it was asked for, so that `Scenario::pack_of` makes the pack of a scenario from the load itself and no list of its files is kept by hand. A path is used as asked, its `..` parts left in. `sim-cli pack` writes packs (`crates/sim-cli/src/pack.rs`), and `sim-cli`'s `save` hashes the data files through the same source |
| `crates/sim-cli` | Command-line runner. Every runner takes its staffs from `sim_staff::staffs()` (decision 0107). `time` plays a trial and a window through `sim-trial` (decisions 0175 and 0177). It has a library target (`src/lib.rs`) holding `seat_trial`, the runner of a seat's trial over `sim-trial`, which `game::open` hands to the session where the scenario names a trial's figures (decision 0178), the function that opens a game for play (`sim_cli::game::open`, with `open_loaded`) and the saved game (`sim_cli::save`), so that a scenario test opens a game as `serve`, `mcp` and `play` do (decision 0182). Since decision 0229, stage 2, the library also holds the server of a seat (`mcp`: `Server`, the tools' definitions and instructions, and `call_seat_tool`, the one function that takes a tool's name and arguments and gives back the text and whether it is a refusal, which the MCP server and the door both call), the tools of a seat whose side has a staff (`staff_tools`) and the game file `play` keeps (`game_file`: its header, its pin, the reading of its calls and their replay, through a `Source`). What stays in the program is what reads standard input or a file named on a command line: `mcp_command.rs` (`mcp`'s command) and `play.rs` (`play`'s command and its writing of the file) |
| `crates/sim-web` | The door of one seat (decision 0229, stage 2): `Door` holds one game, opened from a pack (`sim-cli pack`), and answers one seat as `sim-cli mcp` does, through `sim_cli::mcp::call_seat_tool`. Its functions are `versions`, `begin`, `tools`, `call`, `game_file`, `resume` and `saved_game`; `begin` and `resume` are the only ones that name a side, and a door that has a game refuses a second. `call` answers `{"ok": ..}` or `{"refused": ..}`, as the table's bridge answers `/call`. `game_file` is a file `sim-cli play` reads, with the seat's reads (`sim_agent::WATCHER_TOOLS`) left out and the calls the game refused kept; `saved_game` is refused until the game is over. A plain library first: `Door` has no binding in it. Since stage 3 the crate is also built as a WebAssembly module (`crate-type = ["rlib", "cdylib"]`) for the target `wasm32-unknown-unknown`, bound for JavaScript by `wasm-bindgen`, pinned to one exact version that `wasm-bindgen-cli` must match (`scripts/web/build.sh` stops if they differ); the binding is one small module, `src/binding.rs`, compiled for the target alone (`#[cfg(target_arch = "wasm32")]`), each bound function one call of the one `Door` held in a `thread_local!` cell. The crate takes the workspace's lints unchanged, `unsafe_code = "forbid"` included: the binding macro compiles under it, and `tests/stage3.rs` reads the source for the word `unsafe`. The `web` profile of the workspace's `Cargo.toml` (release with overflow checks written out) is the profile both the module and `door` are built in Its program `door` (`src/bin/door.rs`) holds a `Door` open and answers requests read as lines from standard input. It is the umpire's side of a seat's door, as `sim-cli mcp` is: it holds the session, which holds the world, and what plays is given the answers of the seat's tools and nothing else. `tests/source.rs` reads its source and bans the umpire's words by name (`umpire`, `into_world`, `at_staff_step`, `transcript`, `handed_in`, `watch`, `standing`, `seat_calls`, `state_hash`, `day_hashes`). Depends on `sim-cli`'s library, `sim-agent`, `sim-core` and `sim-data`; `sim-cli` has it as a dev-dependency, to test it against `play` where that program is built |
| `web` | The browser's build and its check (decision 0229, stage 3): `check.mjs` runs the module in node on the very files the build ships and compares every answer and the saved game, byte for byte, with the native `door` program over its line protocol; `games/` holds the game files it plays (one for each scenario the table offers a person against the engine, and four of orders); `offered.mjs` gives the list; `support.mjs` is what the games share. `scripts/web/build.sh` makes `target/web/module/` and `target/web/pack.json`. These are the umpire's: they hold the pack, which holds both sides' starting state. The page's own script and the worker come with later stages |
| `crates/sim-agent` | Agent interface: the daily briefing, the list and detail queries, `explain`, `measure`, and the session a seat plays through (`issue_orders`, `end_day`), as JSON with schemas in `schemas/` (decisions 0048 to 0050). Every tool takes a `SideView`; only `session.rs` holds the world. The MCP server that wraps it is in `sim-cli` (decision 0051). It defines the trait a seat's trial is begun and stepped by (`TrialRunner`, `TrialUnderWay`), what is asked (`TrialAsked`) and the narrow answer (`TrialAnswer`), and is handed the runner by its caller, as its staffs (decision 0178) |
| `crates/sim-staff` | The staff and its doctrine (decision 0107, step 3, stage 1): `SupplyStaff`, the doctrine for keeping a base supplied, its projection of days of supply and its proposals; `DOCTRINE_VERSION`; `staffs()`, the staff of each side every runner passes. Depends on `sim-core` only. Forbids floating point, as `sim-core` does, because its decisions reach the hash. Every function in it takes a `SideView` (with plain numbers) and nothing else; `tests/source.rs` reads its source to check, and bans the world, `at_staff_step` and a side's half of a picture of a world (decision 0171) by name |
| `crates/sim-trial` | Trials (decisions 0174 to 0177, steps 4 to 7 of step 3's stage 4): the pictures of a world a side may be tried in, made from its view, what the scenario says it believed and a trial's figures, the enemy's half by the written rules of `docs/rules/09-the-trial.md` with the list of what was assumed, the world built from a picture, and the playing of a trial: a course in each world for a horizon of days, with both sides' staffs, a world's day at a time; the estimate read from a trial's worlds; and the window, one course at two or three dates in the same worlds. Depends on `sim-core` and `sim-staff` only (`sim-data` for its tests): it is handed the believed forces, intents and men, the trial's figures (`sim_core::refdata::TrialFigures`, which `sim-data` loads, since only `sim-data` reads files and `sim-data` may depend on `sim-core` alone), the reference data and the map as values. Forbids floating point. It reads a `SideView` and the scenario's beliefs and nothing else of a live game: `tests/source.rs` reads its source, allows the world only to build one from a picture and keep it, lets it hand in commands to and resolve with the staffs only a world it built, and bans the umpire, a whole picture, a rebuild on a live seed and a view taken from a world, but in three parts: the play, on one line, to record each day's bases, the first day's plan orders and, on the day the course is taken in, the plan orders and the landings formed (with the side's own command state through that view, on one line); the making of an estimate (decision 0176, amended 14); and the window, on one line in one function, the enemy side of a world it built on a date's eve (decision 0177, amended 7). It takes no world from outside: every world it names it built (decision 0175) |
| `crates/map-tool` | Generates the hex map of the slice from open coastline data, and renders it, locates points and finds sea paths. May use floats and its own dependencies. Nothing but the `tests` crate depends on it, as a dev-dependency (scenario 4b's test places the anchors with its projection) |
| `crates/oob-check` | Checker for the order-of-battle facts in `data/oob`. Depends on nothing else in the workspace |
| `crates/oob-derive` | Derives ship class figures for a list of real ships from `data/oob` and `data/derivation` (decision 0020). Depends only on `oob-check`; `sim-data` and `sim-core` only in its tests. The `tests` crate has it as a dev-dependency: scenarios 114, 120 and 121 ask a list's check of its library (`run` and `said`, which is what the program prints), not of the program through cargo |
| `data/reference` | Ship classes, port sizes and aircraft types as CSV; search, surface combat and air combat figures as TOML. Files `oob-derive` generates (a ship class file `<name>.csv` with `<name>.sources.csv` and `<name>.ships.csv`, and an aircraft type file with its own `.sources.csv`) say so in their header and are never edited by hand |
| `data/derivation` | The derivation rules and constants (`rules.toml`) and one ship list per scenario, for `oob-derive` |
| `data/map` | The generated map of the slice as CSV (`south_pacific.csv`, decision 0017) and the anchorages it was generated with (`south_pacific_anchors.csv`), and small hand-drawn placeholder maps as TOML |
| `data/scenarios` | One TOML file per scenario: starting state, seed, scripted orders |
| `data/oob` | Order-of-battle facts: sourced historical statements as CSV. Research, not simulation data. Start with its `README.md` |
| `docs/research/oob` | The facts format, the source policy, where sources disagree, and a note per battle and per topic |
| `tests` | One test file per scenario, each with its hand calculation written out |
| `scripts` | Commands for working on the repository, not parts of the game: shell scripts run from the top of the repository, each described in `docs/commands.md` |
| `viewer` | The read-only replay viewer (decision 0018): one HTML page with no build step, its check script, and `replays/` (git-ignored) for exported runs |
| `table` | A prototype of the player's interface (decision 0154): a bridge that serves one seat's tools to a browser on this machine, and one HTML page with no build step. It plays the game: it is given a seat's tools and the map file and nothing else |

Crate boundaries:

- `sim-core` depends on nothing, not even other workspace crates. Keep it that way.
- Only `sim-data` reads simulation data files, from the disk or from a pack that `sim-data` itself made. The simulation never reads `data/oob`; only `oob-check` and `oob-derive` do.
- `sim-cli` and the tests are the umpire. They may read truth through `World::umpire()`.
- Anything that plays the game (the staff planner, an agent, the UI) gets a `SideView` and nothing else.
- The staff is passed in. `sim-core` defines the `Staff` trait (given a side's view, it hands in orders, staff commands and reasons) and the function that resolves a day takes each side's staff or none (`Staffs`), so `sim-core` still depends on nothing. Every loop that resolves days passes the staffs it is given: the session, `run`, `batch`, `export`, `hash`, `events`, `time` and `replay --check-staff`. `sim-agent`'s session is handed its staffs by its caller and still depends on `sim-core` only. `sim_staff::staffs()` is the one place a runner gets its staffs, and `sim_staff::DOCTRINE_VERSION` the doctrine version (decision 0107). `sim-agent` may have `sim-staff` as a dev-dependency, for its tests only. Its session alone takes `World::at_staff_step()`, the copy of the world at the step a staff is asked, and hands the staff and the tools only a `SideView` of it.
- `sim-trial` depends on `sim-core` and `sim-staff` only. It is given a side's view and what the side believed, never the world, the umpire's view or the full log; it builds worlds from pictures, plays them, and hands nothing of them back to a live game (decisions 0174, 1, and 0175, 6).
- A seat's trial is played by a runner the session is handed, as it is handed its staffs. `sim-agent` defines the trait (`TrialRunner`, `TrialUnderWay`), what is asked and the narrow answer, which holds no more than a seat may be shown; `sim-cli` (`seat_trial`) implements it over `sim-trial` and `game::open` hands it in only where the scenario names a trial's figures. `sim-agent` still depends on `sim-core` only and never names a world built from a picture (decision 0178, 1, 5 and 6).
- `sim-agent` depends on `sim-core` only. Its library code takes a `SideView` and never the world, the umpire's view or the full event log; a test reads its source to check.
- The replay viewer (`viewer/`) is an umpire's tool like `sim-cli`: it shows the truth. Nothing that plays the game may use it or the replay files.
- The table (`table/`) plays the game. It reads the answers of one seat's tools and the map file, and never a replay, a save, a batch file, the event log or a scenario file (decision 0154).
- `sim-cli validate` (`crates/sim-cli/src/validate/`) reads `data/validation` and a batch file, and writes reports under `docs/validation/`. It is the umpire's tool and shows the truth: nothing that plays the game may depend on it or read its reports. A test reads `sim-agent`'s manifest to check.
- `sim-cli validate --passages` (`crates/sim-cli/src/validate/passages.rs`) reads `data/oob/place_positions.csv` for the positions of the places a passage names, and nothing else under `data/oob`. It is the umpire's tool and not the simulation: the simulation still never reads `data/oob`. It reads the file with a small reader of its own (the `csv` crate, four columns), not `oob-check`'s, so `sim-cli` stays free of that crate.
