# Commands

What each command of the workspace does. `CLAUDE.md` lists the commands themselves; this page explains them. It was moved out of `CLAUDE.md` on Nov 12, 2026 to keep that file short.

`serve SCENARIO --seat allied=player --seat japanese=script` holds a game open and takes one JSON request a line on standard input (decision 0050). `mcp SCENARIO --seat allied` serves the same game and tools as a Model Context Protocol server on standard input and output, and `play --game FILE ... TOOL [ARGUMENTS]` makes one call to it and exits, keeping the game as a file of the calls made (decision 0051); `play` alone prints how. `play --export-save FILE` is refused, with a plain message and exit status 1, until the game is over (a saved game holds both sides' orders); `--export-transcript` alone is allowed at any time, as it holds only the seat's own calls (decision 0085). `.mcp.json` starts that server for Claude Code in this folder, on the full slice with the player as the Allied side (decision 0051, added on the designer's word); edit its last arguments for another scenario or seat. `run --save FILE` writes a saved game (the scenario's name, the seed, each day's orders and the daily hashes); `replay FILE` runs it again and fails on the first day whose hash differs, and refuses a scenario or data file that has changed; `hash` prints the daily hashes only (decision 0043). `events SCENARIO_OR_SAVE --unit HANDLE [--day N]` is the umpire's question to a finished run: it prints every event that names a ship, task force, air group, base or contact in the text `run --events` prints (a ship's task force's events too, marked `via`), and `events ... --why EVENT` prints one event and its causes down to orders as a tree (decision 0052, item 9). `export SCENARIO_OR_SAVE --out FILE` runs a scenario exactly as `run` does, or replays a saved game as `replay` and `events` do (same refusals: a changed file, a missing `--reference`, `--seed`), and writes it as one replay file for the viewer (decision 0018; version 3 also carries each aircraft type's strike radius, extended reach and search range, and each air group's type number, for the viewer's air layer: `viewer/README.md` has the format); a saved game's replay is titled with the game's file and its scenario, so a recorded game is shown on the map with `export crates/sim-cli/tests/recorded_games/NAME/save.json --out FILE`. It also takes `--seed N` (a scenario only) and `--labels data/map/south_pacific_anchors.csv`. `batch` runs a scenario over many seeds (`--runs N`, default 1000, `--first-seed S`, default 1, `--label TEXT` to record the caller's name for the engine, such as a revision; decision 0057) and writes one summary file of losses per side, per ship and per run, and, for each run, the counts step 2's measures read: hits by ship and weapon, gun and torpedo fire by side, systems out, aircraft lost by group and cause, aircraft ready at the end of each day, claims by side, attacks, escorts, break-offs and base supply, the gun and torpedo shots each ship fired, and, for each surface fight, who sighted first and the rounds each force was surprised, and every strike launch with its aircraft, hex, whether it found nothing and the task force its raid met (decision 0062; the file is version 5). It is the umpire's file and shows the truth. `run`, `replay`, `hash`, `events`, `export` and `batch` take `--reference DIR`: the scenario's reference files (ship classes, port sizes, aircraft types, and the search, surface combat, air combat, air upkeep, fatigue and base supply figures) are then read by file name from DIR, in place of where the scenario names them, and one that is not in DIR is an error; the map is read where the scenario names it. `--reference data/reference/step1` runs a scenario on the figures frozen at the end of step 1, which the hand-calculation tests use. A saved game or a batch made with it records DIR's files and their hashes as its inputs, and `replay` and `events` on that game need the same `--reference` and the same files; without it they refuse, saying the scenario now names different data files. `serve`, `mcp` and `play` do not take it. Open `viewer/index.html` in a browser and pick the file. `node viewer/check.js viewer/replays/*.json` checks replays against the page's own rebuild.

The map tool also has `locate --lat --lon`, `path --from q,r --to q,r`, `sides --hex q,r` (a hex's closed sides and neighbours), `water --lat --lon` (why a position's hex has the water it has) and `generate`, which rebuilds `data/map/south_pacific.csv` from the Natural Earth files under `references/` (the exact command is in the file's header). `generate --anchors data/map/south_pacific_anchors.csv` applies the listed anchorages (decision 0017, decision 6); without it hexes keep their largest body of water. `render` draws `#` land, `+` coast, `%` coast with a closed side toward water and `.` sea, each row labelled with its r and the q of its first hex.

`oob-derive` derives ship classes for a list of real ships from `data/oob` (decision 0020). A ship list that generates class files has a `[class_ids]` table giving each class id and the ships that have it (decision 0077): the tool makes one row for each pinned id, in id order, never merges two, and refuses ships pinned to one id whose figures differ, a ship with no id, a pinned ship not in the list, and an id or ship pinned twice; a row of a class with a twin of equal figures is named with its ships in brackets. A ship list may name working assumptions (unknown radar means none, decision 0019; main-gun ammunition not limiting, decision 0023; surface weapons not modelled, decision 0029), may ask for the air figures and may list aircraft types to derive, and the rules file names every exception. With any problem it writes nothing and lists every problem; `--check` only reports; `--facts DIR` reads another facts directory. A list may also have an `[experience]` table (and no class ships) that derives each listed ship's experience value from four yes or no questions and writes `ship_experience_*.ships.csv` (decision 0064, "As built (the derivation)"); a value that rests on a navy's statement with no second source is marked `provisional`. An answer may take its period from the row's own dates and may use a force's statement with `named_by` rows. The rules file's `[fire_rate]` block (decision 0070) names the cases from `engagement_outcomes.csv` and `engagement_events.csv` whose median is the achieved rate of each kind of battery; a class's `gun_rounds_per_min` is the lesser of its sourced rate and that, and the header of a class file that derives surface weapons has an "Achieved rates of fire" section after the exceptions (a list with no surface weapons modelled has none). A run and `--check` print, after the files, the rows of the listed ships that no question read; they are not written to the generated file, so a new row does not make it stale. The rules file's `[search_radius]` block (decision 0075) gives each aircraft type a search range of its own, a third of its range in the scouting condition rounded down, with exceptions read for that alone; a type whose range it cannot settle keeps its strike radius, and a run and `--check` list it as not settled.

`validate BATCH.json MEASURES.toml [--out FILE] [--reference DIR]` judges a batch against a battle's measures file under `data/validation` by the rule of agreement in `docs/step2-spec.md` and writes a markdown report, by default `docs/validation/<battle>-<label>.md`, where the label is the batch's tuning round. It takes each measure's number from every run by the measure's `take` (`data/validation/README.md`), in whole numbers only (`shots_in_hundreds` and `shots` take either a `side`'s shots or the summed shots of a list of `ships`, never both; `shots` counts whole shells, or tens with `unit = "tens"`, summed and divided before it is rounded down once, decision 0084): a percentile is the value at place ceil(p x n / 100) of the kept runs, sorted; the Allied margin is ordered by its exact decimal value. A judged measure that agrees with no part of its record from the 25th percentile to the 75th is marked "agrees, at the edge": it still agrees and the battle still passes on it, but the report's head counts it apart from plain agreements and misses, and lists it under "At the edge" with its spread (a miss's spread now carries the 25th and 75th too). The console line reads `judged N, agree A, at the edge E, miss M`. It refuses a batch with no label, a label that is not letters, digits, dot, dash or underscore, a batch that is not version 5, one made with another state hash layout, one whose scenario or data files have changed (give the same `--reference` the batch was made with), measures of another scenario, and a measure it cannot take. Since version 4 it has two takes for the fights' sighting record, `fights_sighted_first` (night fights whose first sighter is one of a list of `allied`, `japanese`, `both`, `neither`) and `rounds_surprised` (the rounds named task forces were surprised in night fights). Since version 5 it has `aircraft_taking_part`: the aircraft launched in ship strikes whose raid met a force of named task forces, with the escorts that went with them if asked. It will not write over a report of the same name unless the bytes are the same. It ends with success whenever it wrote its report, whatever the verdicts. `validate MEASURES.toml [--out FILE]` is for a measures file with no scenario (not built): every measure is reported as not run. No file under `data/validation` is in that state since Cape Esperance's check (decision 0072, "As built (the check)"). It is the umpire's tool; nothing that plays the game uses it.

`validate --passages data/validation/passages.toml --label TEXT [--map CSV] [--places CSV] [--out FILE]` works each ship passage of the file as one calculation, not runs, and reports it beside the record; no passage is judged. A passage's ends are rows of `data/oob/place_positions.csv` (`from_row`, `to_row`; `--places` names another file) or positions (`from_lat`, `from_lon`, `to_lat`, `to_lon`, decimal strings); each is put in a hex in whole-number arithmetic by the projection of decision 0017, and a place is at the centre of its hex. The charged miles are `Map::sea_charged_nm` (decision 0058) on the map (`--map`, default `data/map/south_pacific.csv`), less `to_short_by_nm`; the minutes are those miles at `speed_kn` with `speed_changes` (minutes from the start of the run), rounded up to the minute the miles are reached. The report is `docs/validation/passages-<label>.md` unless `--out` says otherwise; the label rule and the refusal to write over a different report are those of the battle reports, and a row id that is not in the places file, a row with no position, a row of another place than the one named, or a passage with both a row and a position are refusals naming the passage. A run whose end is land or off the map, or with no sea route, is reported as not worked and the others are still reported. It is the umpire's tool; nothing that plays the game uses it.
