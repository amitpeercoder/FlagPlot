# Commands

History of this page, which options came in under which decision and how a figure or a version used to stand, is in `docs/commands-history.md`; this page says what each command does and takes today.

What each command of the workspace does. `CLAUDE.md` lists the commands themselves; this page explains them. It was moved out of `CLAUDE.md` on Nov 12, 2026 to keep that file short.

`serve SCENARIO --seat allied=player --seat japanese=script` holds a game open and takes one JSON request a line on standard input (decision 0050). `mcp SCENARIO --seat allied` serves the same game and tools as a Model Context Protocol server on standard input and output, and `play --game FILE ... TOOL [ARGUMENTS]` makes one call to it and exits, keeping the game as a file of the calls made (decision 0051); `play` alone prints how. The tools' `measure` takes a fifth question, `{"question": "yard", "task_force": "task_force:N"}`, which answers whether a `send_to_yard` order given now would be refused and why, the port and passage, each ship's days of repair, the days away, the day the force would be back and whether that is before the game's last day, or for a force already away its port and day of return (decision 0069). The `air_reach` answer of `measure` also gives the group's `transfer_range_nm`, the farthest base a `rebase` order can name; the briefing's air group line and `get_entity` give `moved_yesterday` (true the day after a move, when the group flew nothing), and the briefing's losses give `air_groups_rebased` and count aircraft written off by a rebase in `written_off` (decision 0091). The tool `list_contacts` also answers `ground_estimates`, the side's estimates of the enemy's men ashore, one for each hex (the men, the day reported and the age in days), in the area if one is given, and left out when the side holds none; the briefing has the same in its `enemy_ashore` part, and in its action part the side's own bombardments, its ships' shell fire and the bombardments of its own bases (decision 0092). `play --export-save FILE` is refused, with a plain message and exit status 1, until the game is over (a saved game holds both sides' orders); `--export-transcript` alone is allowed at any time, as it holds only the seat's own calls (decision 0085). A game file is pinned to its inputs (decision 0172, 1): the header of a new game file records, under `inputs`, the seed the game is played on, the hash of the scenario file and of each data file it reads (by the means a saved game uses) and the rules version, and before every later call or export `play` compares them with what is on disk; where one differs the call is refused, with exit status 1 and a message that names the file changed (or the rules version), and nothing is written. A game file made before has no `inputs`: it is exported as before, and a new call on it is refused unless the caller adds `--unpinned`, which continues it as it is and leaves it unpinned (`--unpinned` is refused on a pinned or a new game file). A game whose day failed the engine's invariants is stopped (decision 0172, 3): that call and every later one is answered "the day could not be resolved: the game has stopped inside day N on an internal error; the operator has the details", the engine's own words go to standard error, `--export-save` is refused saying the game stopped inside day N, and the transcript holds each answer; the saved game `serve` and `mcp` write at exit for a stopped game carries `stopped_inside_day`. `.mcp.json` starts that server for Claude Code in this folder, on the full slice with the player as the Allied side (decision 0051, added on the designer's word); edit its last arguments for another scenario or seat. For a scenario with objectives, `run` prints the umpire's result after the final state: each side's points by objective with its count (a base's "of N days", ships out of action's "over N days", the horizon), the total, the margin and the outcome, then for `ships_out_of_action` one line for each ship counted with her days at the end, the days she left for a yard with, her days out, her share and her points (decision 0088), and the history note. For a scenario for play (`for_play = true` in its `[objectives]` table, decision 0187) the result is printed under "Result (the scenario's own scale, for play):" in place of "Result (the placeholder scale of decision 0054):". A base an objective names that is not on the reading side's map is written by its hex, "(3,-4)", in the result's lines (decision 0186). In a scenario with land units `run` also shows them, and shows nothing of them in one without (decision 0066): a ship line ends with ", N men of land_unit:M aboard" when she carries men, a base a landing formed ends with ", formed in play, on its own side's map only", and after the bases it prints one line for each land unit with its side and either "N men ashore at (q,r)" or "no men ashore", with ", on attack" and ", fatigue N" when the unit is on attack or tired, and an air group lost with its base is shown as "lost with its base" (decision 0090); its events (men embarked and landed, a base formed, a unit divided, men fed, men lost and a unit destroyed) are in the `--events` text, each with its causes. After the final state `run` also prints each side's estimates of the enemy's men ashore, one line for each, "Allied estimate at (q,r): N enemy men ashore, reported day D", and prints none for a side that holds none, so a game with no ground report reads as it did (decision 0092); a bombardment (a ship's fire and the force's), men lost to fire, a ground report and a base found are in the `--events` text with their causes. `run --save FILE` writes a saved game (the scenario's name, the seed, each day's orders and the daily hashes); `replay FILE` runs it again and fails on the first day whose hash differs, and refuses a scenario or data file that has changed; `hash` prints the daily hashes only (decision 0043). `pack SCENARIO... --out FILE [--reference DIR]` writes the pack of the scenarios named (decision 0229, rulings 9 and 10): `sim-data` loads each scenario through a source that notes every file it is asked for, and the files so read are written as one JSON object, `{"versions": {"rules", "state", "doctrine"}, "files": {path: text}}`, the versions being those of the program that made it. A path is as the load asked for it, with its `..` parts left in, so run it from the top of the repository to have the repository's own (`data/scenarios/table-boats/../../map/midway.csv`). The pack holds exactly the files the loads read and no others. It is the umpire's file: it holds both sides' starting state. `resolve SCENARIO` reads a scenario built on another (a file that states `built_on`, decision 0234) whole: it prints the resolved scenario as TOML on standard output, with no `built_on` and every file name written for the folder of the file asked for, so that the text put in that folder loads as the overlay does, and the files read, the one asked for first, a path a line on standard error. A file with no `built_on` is printed as its table. It builds no world and reads no file but those of the chain. It is the umpire's tool. `sh scripts/overlay-proof.sh REV [COUNT]` holds each file that states `built_on` against the same file as it was at REV (the commit the branch left `main` at): the two `resolve` texts must be byte for byte the same, and the two `run --events` texts the same; it lists each file with `same` or `DIFFERS`, counts them, and exits 1 on any difference or when the number of overlays is not COUNT. `SIM_CLI` names the program to use. `events SCENARIO_OR_SAVE --unit HANDLE [--day N]` is the umpire's question to a finished run: it prints every event that names a ship, task force, air group, base, land unit, submarine (`submarine:N`, decision 0218) or contact (`land_unit:N`, the engine's number, as the umpire's tools use) in the text `run --events` prints (a ship's task force's events too, marked `via`), and `events ... --why EVENT` prints one event and its causes down to orders as a tree (decision 0052, item 9); beneath an event that a command passed on as a report it prints each "report sent" event of that report, with the commands it was sent to and when it arrived (decision 0135, item 22). `export SCENARIO_OR_SAVE --out FILE` runs a scenario exactly as `run` does, or replays a saved game as `replay` and `events` do (same refusals: a changed file, a missing `--reference`, `--seed`), and writes it as one replay file for the viewer (decision 0018; a base that changes side is listed in `base_changes`, decision 0090; a bombardment, men lost to fire, a ground report and a base found are events of the file, and the final state lists each side's ground estimates, left out where none is held, decision 0092; version 3 also carries each aircraft type's strike radius, extended reach and search range, and each air group's type number, for the viewer's air layer; version 5 adds to each base record, from the same records, `ammunition` (tons, left out when 0), `airfield_closed` (true for an airfield whose damage is at or above `airfield_landing_refused_at`, left out when false) and `days_of_supply` (the holder's days of supply in the base's hex at that step, as `SideView::days_of_supply` works it, left out where it has no figure and in `initial`), for the viewer's base panel and base marks, and is otherwise version 4; version 4 also carries `steps`, the state at the end of each step of every day as the records that changed since the step before, made by running the scenario through `World::resolve_day_watched`, so that the viewer draws the state and does not work it out from the events, and is otherwise the file of version 3: `viewer/README.md` has the format); a saved game's replay is titled with the game's file and its scenario, so a recorded game is shown on the map with `export crates/sim-cli/tests/recorded_games/NAME/save.json --out FILE`. It also takes `--seed N` (a scenario only) and `--labels data/map/south_pacific_anchors.csv` (or `data/map/midway_labels.csv`, the places of the Midway map). The replay's `map` carries `frame` for a generated map, as its header gives it (centre, factor, western and eastern edge, longitudes in the map's run, so 194 for 166 W; decision 0199), and none for a hand-written one. `batch` runs a scenario over many seeds (`--runs N`, default 1000, `--first-seed S`, default 1, `--label TEXT` to record the caller's name for the engine, such as a revision; decision 0057) and writes one summary file of losses per side, per ship and per run, and, for each run, the counts step 2's measures read: hits by ship and weapon, gun and torpedo fire by side, systems out, aircraft lost by group and cause (aircraft written off by a rebase are counted with those worn out, in `worn_out`), aircraft ready at the end of each day, claims by side, attacks, escorts, break-offs and base supply, the gun and torpedo shots each ship fired, and, for each surface fight, who sighted first and the rounds each force was surprised, and every strike launch with its aircraft, hex, whether it found nothing and the task force its raid met (decision 0062; the file is version 6 since decision 0138, which adds each run's `refusals`; version 5 before it). The header carries `for_play`, always written, true or false, after `label` and before `runs`: it says whether the scenario is for play (decision 0187; added at version 6, whose number is unchanged, and a file without it is of record). A run that lost any man has `men_lost`, the men each side lost by cause (`fight`, `unfed`, `lost_with_ship`, `fire` and `surrendered`), and a run with a bombardment has `bombardment_shells`, the shells each side fired; both are left out of a run with none, so the version stays 5 (decision 0092). For the land fight a run also has, each left out where empty: `men_lost_by_day` (`day`, `japanese`, `allied`: the men lost that day by every cause), `airfields_built` (`day`, `base`), `arrivals_delivered` (`day`, `air_group`, `aircraft`) and `ashore_by_day` (`day`, `side`, `q`, `r`, `men`, `supply_t`: the men ashore at the end of each day and the supply of the side's bases in the hex); the batch's header has `daily_supply_t_per_man` when the scenario has ground figures. `validate` has the takes `base_holder`, `men_lost`, `airfield_built_day`, `arrival_day` and `days_of_food` for them (`data/validation/README.md`). It is the umpire's file and shows the truth. `run`, `replay`, `hash`, `events`, `export` and `batch` take `--reference DIR`: the scenario's reference files (ship classes, port sizes, aircraft types, and the search, surface combat, air combat, air upkeep, fatigue, base supply and ground figures) are then read by file name from DIR, in place of where the scenario names them, and one that is not in DIR is an error; the map is read where the scenario names it. `--reference data/reference/step1` runs a scenario on the figures frozen at the end of step 1, which the hand-calculation tests use. A saved game or a batch made with it records DIR's files and their hashes as its inputs, and `replay` and `events` on that game need the same `--reference` and the same files; without it they refuse, saying the scenario now names different data files. `serve`, `mcp` and `play` do not take it. Open `viewer/index.html` in a browser and pick the file. `node viewer/check.js viewer/replays/*.json` checks replays: the steps of a version 4 file against its final state and against the page's own rebuild from the events.

`cargo run -p sim-web --bin door` holds a game of the door of one seat open and answers requests read as lines from standard input (decision 0229, stage 2): each a JSON object `{"function": NAME, "args": [..]}` with the arguments as strings, and each answered by one line, `{"ok": TEXT}` with the door's own string or `{"error": WORDS}`. The functions are the door's: `versions`, `begin` (the path of a pack file, as `sim-cli pack` writes it, and a request `{"scenario": PATH, "seat": "allied"|"japanese", "seed": "DIGITS" or null}`), `tools`, `call` (the tool and its arguments as JSON text), `game_file`, `resume` (the path of a pack file and the text of a game file) and `saved_game`. A game file it gives is one `play` reads, without the reads; the saved game is refused until the game is over. It is for tests and for the check that compares the browser's build with the native one; it is not a way to play.

`serve ... --watched` (decision 0182) opens a watched game: the watcher holds the clock and the seats' calls of time wait for him (rules chapter 1, A watched game). A seat's call is as above, except that a call of `end_day`, `run` or `advance` whose arguments stand is held, with no answer line until a step brings its stop; its answer line, with its own `id`, then follows the step's line (two due on one step, the Allied first). Requests beside a seat's call: `{"id": N, "watcher": "step"}` takes one pulse where the scenario has orders inside a day, one day where it has not, and is answered with `{kind: "step", resolved: {day, pulses}, clock, stops, game_over, summary}`, or an error naming a played seat that is not ready; `{"id": N, "watcher": "read", "side": "allied", "tool": T, "arguments": {..}}` is a read of the watcher's (get_briefing, list_forces, list_bases, list_contacts, get_entity, measure, explain, events, command_state, plans, staff_orders, propose, order, why, report, trials), answered as that side's seat would be and entered in no transcript; `{"id": N, "watcher": "standing"}` gives where the game stands (`kind: "standing"`); `{"id": N, "watcher": "seat_calls", "side": "allied"}` gives what a seat did since its last stop (`kind: "seat_calls"`); `{"id": N, "seat": "allied", "request": "tools"}` and `"request": "instructions"` give the seat's tool definitions (`{"tools": [..]}`) and the words an agent is given on taking the seat (`{"instructions": ".."}`), as `mcp` gives them. Without `--watched` none of these is a request and each is answered as any request that is not a call is. A watched game left inside a day is saved with `stopped_inside_day`, and the saved game replays without a watcher to the same hashes. The table's bridge holds one such game: `python3 table/serve.py SCENARIO --watch --seat allied [--seat japanese]` starts `serve --watched` with those seats the agents' (the other the script's), prints the watcher's page (`http://127.0.0.1:PORT/watch/KEY/`) and one door for each agent's seat (`http://127.0.0.1:PORT/seat/KEY`), each key new at every start; a door takes `POST /call` with `{"tool", "arguments"}` and `GET /tools` and `/instructions`, holds a call up to `--hold` seconds (50) and then answers `{"waiting": true, ..}`, and its own tool `wait` collects the answer; `--keep DIR` keeps the saved game and the transcripts (one file for the game and one a seat) in DIR on leaving. `python3 table/seat_mcp.py --url DOOR` offers one door as a Model Context Protocol server on standard input and output. `python3 table/check_watch.py` checks the bridge, the doors and `seat_mcp.py` by script; `table/README.md` has the rest.

Units made ready and a base built up (decision 0141, agent interface version 18): `set_intent` takes `intent_kind` `ready_landing` (`task_force`, `hex` as `[q, r]` and an optional `by_day`, a whole number from 1, and no `base`) and `build_up` (`base`, `wants`, a list in order of `airfield`, `mend`, `defences`, `port` and `aircraft`, each at most once, and `defences`, the points from 1 to 100, required when `defences` is a want and refused otherwise), written the same in a scenario's `[[command]]`, in `form_intent` and in a saved game. A forces limit takes `land_units` (the side's land unit numbers, in a scenario the ids), `hold` and `release` take `land_unit` as their one target, and the staff's notices include `ready`, `late` and `met`. `command_state` gives `by_day`, `wants` and `defences` in an intent (`null` for the other kinds), `land_units` in a forces limit and `land_units_binding` in `limits_read_up`.

Taking a place (decision 0142, agent interface version 19): `set_intent` takes `intent_kind` `take_place`, an end addressed to the area: in a scenario's `[[command]]`, in `form_intent` and in a saved game it takes `hex` as `[q, r]` and an optional `by_day` (a whole number from 1) and no `base`, `task_force` or other key; the `set_intent` tool of a seat takes exactly one of `hex` and `base`, where `base` is the number of a base on the side's map that is not the side's and the tool writes that base's hex (a base that is not one of those is refused with a message saying so). The engine refuses a hex that is not land with `{hex} is not a hex of land on the map`. `command_state` gives for a take_place its `hex` (the place) and `by_day`, and a new key `phase` on every intent: `prepare` (its plan is preparing), `move` (released, no man of the side ashore at the place) or `land` (released, and one is), `null` for every other kind. The staff may now hand in `set_limit` of forces, only on an intent it formed (the land units and ships of the landing it readies under a take_place), as the saved game's staff hand-in and the report show.

Ashore, and holding a place with men (decisions 0143 and 0144, agent interface version 20): under a take_place the staff judges each morning, once its men are ashore, and may send a second lift, its `set_limit` of forces on the ready_landing it formed (shown in the staff's hand-in and the report as for any staff limit). A `set_intent` of `hold` may name a base on the side's map that is not the side's, an enemy base; the engine accepts it and the staff waits until the base is the side's, and the `set_intent` tool says so. The staff's `form_intent` may be `keep_supplied` under a hold, with `intent_kind` `keep_supplied`, `base`, `floor_days` (a whole number, 0 allowed) and no `interval_days`; where it has no forces limit of its own it uses the hold's, read up the tree, and it is written with the same keys in a saved game (still version 16) and in a hand-in. The `staff_notice` event in the export may carry an optional `intent` (the intent's number, only for the `met` notice of a take_place), and that notice now says "intent:N is met". The doctrine version is `supply-24`.

Bombarding a base (decision 0146, agent interface version 21): `set_intent` takes `intent_kind` `bombard`, a task addressed to the task force: it takes `task_force` and `target` and no other key, and means: bombard a base on your map that is not yours with your task force on the bombardment mission. It is written the same in a scenario's `[[command]]` (`intent_kind = "bombard"`, `task_force`, `target`), in `form_intent` and in a saved game, and it may stand under a `neutralise` of the same target or under a `take_place`. `command_state`, `propose` and `plans` give the kind with its `task_force` and `target` (its `base`, `hex`, `by_day` and `phase` are `null`).

The force assembled by the staff (decision 0149, agent interface version 23): a `take_place` may have no forces limit, or a forces limit (`set_limit`) naming any of `task_forces`, `land_units` and `source`; the engine no longer refuses one with no source. On the first morning its plan is preparing the staff chooses what the commander left out: the source by the lift each base of the side gives (its transport force stopped there and the fighting units ashore there that the staff may take), the units, the transport force and the forces on the bombardment, carrier and escort missions it may take; it keeps its choice as the forces limit of the `ready_landing` it forms, naming only what the commander did not. `command_state` reads what binds an intent on the chain as it binds: the commander's where he named it, the staff's choice where he did not. Scenario 74 (`data/scenarios/74_the_force_assembled.toml`) plays it.

Controlling an island (decision 0151, agent interface version 24): `set_intent` takes `intent_kind` `control_island`, an end addressed to the area: it takes `island` (required, the number of an island of the scenario) and an optional `by_day` (a whole number from 1, given to each take the staff forms under it) and no `base`, `target`, `task_force` or `hex`. In a scenario's `[[command]]`, in `form_intent` and in a saved game it takes the same keys. An island is map data: a scenario names it in an `[[island]]` table with `number`, `name` and `places = [{ base = N } | { hex = [q, r] }, ...]` in order, a base place meaning its base's hex; the loader refuses an island with no place, a number used twice, a base place that names no base of the scenario, a hex place off the map or not a coast hex, and a place with both keys or neither. An island the scenario does not have is refused with `island N is not an island of the scenario` (reason "No such island"). The intent needs no forces limit and is never marked complete; under it the staff forms take a place, hold a place, deny an area and neutralise a base, and operate a carrier force under the denial, each with a plan of its own for a take and for a keep supplied under a hold. `command_state` gives `island` on every intent (`null` but for a control_island) and, for a control_island, a `measure` (days in force, days controlled and each named place with its hex, whether it is the side's and its days of supply today); `report` gains `islands`, the measure of each island intent in force, with the words "controlled on N of M days in force". The staff's `withdraw_intent` is now in its hand-in: it withdraws a neutralising it formed under an island whose base has become the side's; on an intent the commander made it is refused as "Not yours", and the commander's own `withdraw_intent` on an intent the staff made is still refused as "Made by the staff". Scenario 76 (`data/scenarios/76_controlling_an_island.toml`) plays it.

Forces with men aboard (decision 0152, doctrine `"supply-32"`, no new tool, key or version but the doctrine's): a transport force with men aboard is a lift as it stands. A take with no forces named takes one with a fighting unit aboard as its first lift before any base, and sends each later one once the first is in, adding its force and units to the "ready a landing" by `set_limit`; a hold sends to its base one no take can use, a hold the staff made having the force added to its forces limit by `set_limit`; under an island each hold's forces limit is set each morning to the source and the transport forces stopped there with nothing aboard, a pool that only grows. `staff_orders` and `why` show the reasons. Scenario 77 (`data/scenarios/77_forces_with_men_aboard.toml`) plays it.

A unit's day (decision 0140, agent interface version 17): a task force, ship, air group or land unit that its side may not yet use has `available_from`, a whole number (the day), in its line in `list_forces` and the briefing and in `get_entity` (a ship also in a task force's `ships`), and the briefing's text says "available from day N"; `command_state` gives `not_yet_available` (each unit with its `available_from`) in a forces limit that names such units and `available_from` on a held force. The field is left out once the day has come for the orders now being given, and no enemy unit has one. An order to the unit is refused with `may be used from day N` (`not_yet_available` in the events export). A land unit's `get_entity` gives its `formation` (`number`, `name`) and `parents`, the formations above it nearest first, where it has them. A scenario gives a day as `available_from` on `[[task_force]]`, `[[ship]]`, `[[air_group]]` and `[[land_unit]]`, and formations as `[[formation]]` with `id`, `name`, `side` and `parent`, a land unit's own as `formation`.

`time --machine TEXT` measures what a day costs, outside the game (decision 0100, 11 to 13): one day of the full slice early (day 2 from day 1) and late (day 13 from day 12), the same day with every question of both sides asked at every moment of it and the asking alone once before the day, a copy of the world (the slice at days 1 and 12, the soak at day 150) with and without its event log (the event log is timed alone and the copy without it reported as the difference), and `--games` (100) games of `--days` (30) from the start of the soak and from its day 150. Two more measure the staff (decision 0107, "What it must pass", Speed): f, a day's staff decisions for one side, the time of `Staff::decide` on the side's view at the staff's step (`World::at_staff_step`) for each day of `--slice` played with the staffs (each day's time is the median of `--repeats` askings, the spread is over the days, and the longest day is named), for each side; and g, a quiet week in one call, seven days resolved in a row with the staffs as `run {days: 7}` does, from the start of the slice and from `--early-day` and `--late-day` (cut short, and said so, where the scenario ends). No number fails them. A copy keeps its seed, so those games are one game played a hundred times: the cost is what a trial of that size pays. Each workload is a spread, min, median and max, over `--repeats` (20) runs (the games one run each), in a release build (a debug build says so), and the report ends with the totals that matter. Last, h, a trial of the Allied side (decision 0175, 9, as amended) on `--trial-slice` (by default `data/scenarios/stage-3-proof/07a_slice.toml`, the 39 days in which each side has its two orders to control an island): from the evening before day 1 with the side's own commands of day 1 in that file as the course, and from the evening of `--trial-late-day` (20), the slice played to it with its own commands and both staffs, with an empty course; at each of the three sizes of the trial's figures (the slice's own where it names a `trial` file, else `--trial-figures`, by default `data/reference/trial.toml`), on their seed, as trial 1; once each, timed from the making of the pictures to the dropping of the worlds, with both staffs. It prints the days played and any world that could not be played, and checks the live game's hash is the same after. `--only-trial` times the trial alone and `--trial-size small|standard|full` one size only (to read the peak memory of one size from outside, as `/usr/bin/time -l` does; the command cannot read it itself). `[[command]]` in a scenario file (decision 0107, item 16) states what a side's commander says on a day, as `[[order]]` states what a side orders: `day`, `side`, `kind` and the keys of the kind, and no other. The commander's kinds only: `set_intent` (`intent`, `base`, and `intent_kind`, which is `keep_supplied` where the key is absent, with `floor_days` and optional `interval_days`, or `cover` or `hold`, which take neither, or `neutralise` (`target`, an enemy base on the side's map, and no `base`) or `raid` (`base` and `target`), or `deny` (`hex` as `[q, r]`, a hex on the map, and `distance` in whole hexes, and no `base`: the waters within `distance` of `hex`) or `strike_ships` (`base`) or `stand_at` and `operate_carriers` (each `task_force`, a task force of the side, and `hex` as `[q, r]`, and no `base`) or `ready_landing` (`task_force`, `hex` as `[q, r]`, a coast hex, an optional `by_day` from 1, and no `base`) or `take_place` (`hex` as `[q, r]`, a hex of land, an optional `by_day` from 1, and no `base` or `task_force`; decision 0142) or `control_island` (`island`, the number of an `[[island]]` of the scenario, and an optional `by_day` from 1, and no `base`, `target`, `task_force` or `hex`; decision 0151) or `bombard` (`task_force`, a task force of the side, and `target`, a base on the side's map that is not the side's, and no `base`; decision 0146) or `build_up` (`base`, `wants` as a list of `"airfield"`, `"mend"`, `"defences"`, `"port"` and `"aircraft"` in order, each at most once, and `defences`, the points from 1 to 100, required where `"defences"` is a want and refused otherwise; decision 0141); `search_waters` (`base`) is read but the engine refuses it, as the staff's alone; decisions 0115, 0117, 0120, 0123, 0124 and 0125), `withdraw_intent` (`intent`), `hold` and `release` (one of `ship`, `task_force`, `air_group` and `land_unit`; `air_group` with `setting = "search_arc"` holds that setting alone and with no `setting` holds the whole group), `set_limit` (`limit` is `forces` with `intent` and, each optional, `ships`, `task_forces`, `air_groups`, `land_units` and `source` (a supply intent's forces limit must name a source, another kind's need not; a `take_place` may have no forces limit, or one naming any of `task_forces`, `land_units` and `source`, and the staff chooses the rest, decision 0149); `area` with `intent` and `hexes` as `[[q, r], ...]`; `priority` with `intent` and `rank`; `protected` with `intent` and `ships`; `reserve` with `base`, `supply_t` and `fuel_t`, whole numbers or decimal strings; `risk` with `intent` and `risk` as `preserve`, `balanced` or `press`; `not_before` with `intent` and `from_day`, `wait_for` with `intent` and one of `task_force` and `land_unit`, and `after` with `intent` and `other_intent`, each with its other key left out to clear it, decision 0159; `knowledge` with `intent`, `knowledge` as `none`, `count` or `recent_count` and, with `recent_count` alone, `within_days`, 3 where left out, `knowledge` left out to clear it, decision 0159, 12), `set_leave` (`leave` as `prepare` or `launch`, and `given`) and `approve` and `cancel_plan` (`plan`). An unknown key, a key the kind does not take, a missing key, a TOML float, a day outside the scenario's days and a kind that is the staff's are refused when the scenario loads; whether a base, ship or intent exists is checked by the engine when the command is taken in, as a refusal event. The commands are kept in the scenario beside its orders (`Scenario::scripted_commands`, `replace_commands`), kept by `with_seed`, and handed in by `next_day_watched` with `World::submit_commands` before the day resolves, so the engine takes them in at the first step of the day. A scenario with none plays as it did.

`command_levels = true` at the top of a scenario file (decision 0134, optional, off by default) turns command levels on: each side has an area command, and each task force with a ship and each base is a command under it, each with a picture of the enemy of its own (chapter 1 of `docs/rules/`, Commands and their pictures). A `[[task_force]]` or `[[base]]` entry may add `superior = { task_force = N }` or `superior = { base = N }` to place its command under another command of its side; the loader checks it and nothing reads it yet. A scenario without the key plays as before.

`reports = "../reference/reports.toml"` in a scenario file (decision 0135, optional) names the report figures, the chances that a report passed between commands arrives on time, a pulse late or never and the radio reach of each kind of ship and of a base. With `command_levels` on, a report is then held first by the command that saw the thing and passed up, sideways and down (chapter 1 of `docs/rules/`, Commands and their pictures); without the key every report reaches every command at once. The file is read where the scenario names it, not through `--reference`, is listed among the data files the scenario names, and a scenario that names it without `command_levels` plays as before.

`class_sides = "../reference/class_sides_full_slice.csv"` in a scenario file (decision 0173, optional) names the file of sides: a hand-written CSV with the columns `table` (`ship_class` or `aircraft_type`), `id`, `side` (`allied`, `japanese` or `both`) and `note`, every row with a note. It is a reference file, so `--reference DIR` redirects it by file name as it does the class files (the frozen step 1 copy has rows for the frozen classes alone), and it is listed last among the data files the scenario names. The loader refuses the scenario where a class or type its reference files give has no row, a row names one they do not give, one is given twice, or a ship or an air group of the scenario is of a class or type the file gives to the other side alone. A side's view answers whose a class or a type is (`SideView::ship_class_side`, `aircraft_type_side`). No rule of play reads it, and a scenario that names none plays as before.

A scenario may state what a side believed of the enemy when the game began (decision 0173, optional). A `[[believed_force]]` entry has `side` (the side that believes it), `name`, `kind` (as a contact's: `carrier`, `battleship`, `cruiser`, `destroyer`, `transport` or `auxiliary`), `ships` (1 or more), `standing` (`present`, `absent` or `unknown`), where it was last known, either `at_base = N` (an enemy base on the side's map) or `q` and `r` (a hex on the map), with `day` (the day it was known there, 0 for before the first day and the default), or neither where the side does not know where, and `placeholder` and `note` (a placeholder needs a note). A `[[believed_intent]]` entry has `side` (the side that believes it), `intent_kind`, which is required, and the keys that kind takes in a `[[command]]` of kind `set_intent`, with no `day`, `kind` or `intent` number, and `placeholder` and `note`. Its kind is one that names only a base, a hex or an island: `keep_supplied`, `cover`, `hold`, `strike_ships`, `deny`, `build_up`, `take_place`, `control_island`, `neutralise` or `raid`; a kind that takes a task force (`stand_at`, `operate_carriers`, `ready_landing`, `bombard`) is refused, since a side cannot name a force of the enemy's (the architect's ruling on decision 0173). It is checked as that command would be checked for the enemy's side (a kind the staff alone may give, such as `search_waters`, is refused), and a base it names must be on the map of the side that believes it. The loader refuses an unknown key, side, kind or standing, no ship, a base of the believing side's own or off its map, a hex off the map, both a base and a hex, a day with no place or after the last day, and an intent the enemy could not be given. Both are kept with the loaded scenario (`Scenario::believed_forces(side)`, `Scenario::believed_intents(side)`): they are not state or belief, are never hashed, change no game, and are shown to no seat. A `[[believed_men]]` entry (decision 0176) states men of the enemy's a side believes may be ashore at a place beyond its estimate: `side`, `name`, `men` (1 or more), `standing` (`present`, `absent` or `unknown`), the place, either `at_base = N` (a base of the enemy's on the side's map, which means its hex) or `q` and `r` (a hex of land or coast on the map), and `placeholder` and `note` (a placeholder needs a note). It takes no `day`. The loader refuses an unknown key, side or standing, no man, no place, both a base and a hex, one of `q` and `r` alone, a base of the believing side's own, not of the scenario or off its map, and a hex off the map or of sea. It is kept as a believed force is (`Scenario::believed_men(side)`).

`trial = "../reference/trial.toml"` in a scenario file (decision 0174, optional) names a trial's figures, for a scenario that is to be tried: a TOML file with a `placeholder` flag, `enemy_base_supply_t` and `enemy_base_fuel_t` (each a whole number or a decimal string, neither below 0), what each base of the enemy's on a side's map is given when the crate `sim-trial` makes the enemy's half of a picture. It is a reference file, so `--reference DIR` redirects it by file name (the frozen step 1 figures have a copy), and it is listed last among the data files the scenario names. It also gives the `seed` every trial draws on (decision 0175, amended point 7), a whole number, and the three sizes of a trial (decision 0175, 2), the tables `[small]`, `[standard]` and `[full]`, each of `worlds` and `days` as whole numbers, at least one world and one day; every key is required. It is kept with the loaded scenario (`Scenario::trial_figures()`): not state, never hashed, read by no rule of play, and a scenario that names none plays as before. Scenarios 93 and 94 name one (94 its own, `trial_placeholder_scenario_94.toml`, with 0 t of supply and fuel and seed 1942).

A scenario may name commanders (decision 0137, optional): a `[[commander]]` entry with `side`, exactly one of `task_force = N`, `base = N` or `area = true`, `name`, `initiative` (`"cautious"`, `"steady"` or `"bold"`) and `note`, what the rating rests on, which is required (every rating is a placeholder). The loader refuses a rating without its note, a commander for a task force or base the scenario does not give that side, an unknown rating and two commanders for one command, whether command levels are on or off. A `[[contact]]` entry may add `seen_by = { task_force = N }` or `seen_by = { base = N }`: with `command_levels` on the contact is then in that command's picture alone, as its own, and sent to no one. With command levels off a commander is not read and `seen_by` changes nothing. The rating is read only by a carrier force's closing (rules chapter 8, Operating a carrier force, items 17 to 19).

`sim_staff::staffs()` is the one place that says which staff a runner passes, and `sim_staff::DOCTRINE_VERSION` under what version (each version of the doctrine and what it added: `docs/commands-history.md`): the staff for both sides, the supply doctrine and, after it, the air doctrine for holding a place and covering a base from the air (decisions 0115 and 0117), which hands in nothing for a side with no intent in force, so a game with no command is the game it was, and the warning of decision 0201 is a reason of a carrier or stand task, so it too needs an intent. A `form_intent` is the staff's alone and is refused when a scenario is read. `run`, `batch`, `export`, `hash`, `events`, `time`, `replay --check-staff` and a game held open for play (`serve`, `mcp`, `play`, through `sim_agent::Session::with_staffs`) all take their staffs from it; `sim-agent` is handed them by its caller and depends on `sim-core` only. A game kept by `play --game FILE` begins with a header line that now holds `doctrine_version`; the game is rebuilt from its calls each time, so it is resumed only under the doctrine it was begun under, and another version is refused with a message naming both ("begun under doctrine version ..., and this program has doctrine version ...; the game is not converted, so begin it again"). A game file made before the key existed has none and is refused: it was begun with no staff. The replay file of `export` also carries each side's command state in `final.commands` and in the steps (`viewer/README.md`), only for a side whose command state is not empty, so the export of every scenario without commands is as it was. Since the intent tree an intent there has a `kind` of `keep_supplied` (with `floor_days` and `interval_days`), `cover` or `hold` (with `base` alone), a `parent` and a `maker` of `"staff"` (each left out for a root made by the commander), a forces limit may have `air_groups` and no `source`, a `risk` is left out where none is set, and a reason has a `chain` (the intents above it, as text); the events `intent_formed` and `intent_withdrawn` (`side`, `intent`, `parent`) are in its event list.

`run SCENARIO` prints each land unit's line with its men ashore and hex, then ", on attack" where the unit is not on defend, ", fatigue N" where its fatigue is above 0 and, since decision 0106, ", fieldworks N" where its fieldworks are above 0; a unit that has dug none has the line it had. `export` writes the final state's land units with `fieldworks` (decision 0106), left out when 0 so that a file made where nobody digs is as it was, as the skills are left out when all are 2 (the rulebook's chapter 7, What a side sees); the events `fieldworks_changed` and `defences_worn` are in its event list. The viewer rebuilds the fieldworks from them (`viewer/README.md`). `events` lists the new events of a unit or a base as it lists any other, and `--why` follows their causes.

A scenario's `[[order]]` for an air group may be `kind = "set_strike_sizing"` with `on` (`true` or `false`): whether the group's naval strikes are sized to the contact (decision 0118; rules chapter 5, A strike sized to its target). A group has no scenario key for it. A scenario's `[[order]]` for an air group may also be `kind = "set_strike_first_waters"` with `hexes` as `[[q, r], ...]` (decision 0190; rules chapter 5, Air group orders), and `kind = "set_search_once"` with `on` (`true` or `false`): whether a group on the search mission flies its search once a day, in the morning, and rests in the afternoon (decision 0131; rules chapter 5). The agent's order of the same name is `{"kind": "set_search_once", "on": true}`. A scenario's `[[order]]` for a task force may be `kind = "escort"` with `charge = N`, the number of another force of its side, or with no `charge` to clear it (decision 0121; rules chapter 1, Task force orders, and chapter 2, Keeping station). The agent's order of the same name is `{"kind": "escort", "charge": "task_force:N"}`, and `{"kind": "escort"}` with no `charge` (or `null`) clears it. In a scenario's `[[command]]`, `intent_kind = "deny"` takes `hex = [q, r]` and `distance`, and `intent_kind = "strike_ships"` takes `base`; the staff forms the strike-ships and search-waters tasks under a deny intent (rules chapter 8, Denying an area). The command report (`report`) gives `denials`, the measure of each deny intent in force, with words, beside `holds` and `neutralisations`. The `measure` tool's `strike` choice answers the contact and, since decision 0118, the aircraft the group would send. The agent's order `set_radio_silence` is `{"kind": "set_radio_silence", "on": true}` for a task force (decision 0136: a silent force sends no state report and none of its own reports up or sideways until it fights, is attacked or launches a strike; off unless a scenario's `radio_silence = true` on a `[[task_force]]` or an order sets it). The answers are version 15 since decision 0136: where command levels are on and report figures are loaded, the briefing, `list_forces`, `list_bases`, `get_entity` and `measure` of the area seat read the side's own forces and bases as the area command last had them reported, and a force's or a base's line carries `as_of` (such as "the morning of day 1", or "the start") where that is not the pulse just ended, left out otherwise, and a force's line carries `radio_silence: true` where it is on; the briefing's text says "(as last reported, of ...)" after the place. With command levels off, or no report figures, every answer is as it was. The staff tools and the checking of an order read the side's own view as before.

**What is known of the enemy** (decision 0226; agent interface version 52). Every seat has one tool more, `intelligence`, listed after `events`: it takes no argument and gives what the seat holds of the enemy on one answer of kind `intelligence`, in the parts `seen`, `lost_sight_of`, `claimed`, `enemy_has_done`, `ashore`, `enemy_bases`, `enemy_submarines` and `before_the_game`, `parts` naming those that hold something in that order and `not_kept` those a seat at a command is not given (rules chapter 1, What a seat holds of the enemy, on one paper). It reads the seat's picture and the side's own events and nothing else, and changes nothing: no state, no hash, no saved game. A watcher has it for the seat watched. The schema is `intelligence.schema.json`.

**What is queued, and taking it back** (decision 0221, rules 15 to 18; agent interface version 46). Every seat has two tools more, listed after `end_day`, so the first twelve tools of a seat are the ten above and these, and `intelligence` (below) is the thirteenth in the list of `TOOLS`; a seat with a staff has the others after them. `queued` takes no argument and lists what the seat has queued: the orders for the next pulse of the open day (queue `pulse`), the orders for dusk, among them those kept for dusk from a stop inside a day (`dusk`), and the commands (`commands`), each in the order given with its place (the queue and its number there, from 1). An order gives its `unit` and its `order` body as `issue_orders` takes them, a command its `tool` and its `command` as the command tools answer them, each in the side's numbers (a ship, task force, air group, land unit or submarine by the number every other tool gives it, never the engine's); both give `text`, `acts` (`{"at": "pulse", "day", "pulse"}` or `{"at": "dusk", "day"}`, the day being the day the entry is given for) and `acts_words`, `goes_with` (the places taken back with it) and `rests_on` (for a hold, the queued orders to its unit). The answer has an `as_of` that changes whenever the queues change or the clock moves. `take_back {queue, number, as_of, reason}` withdraws the entry at a place and what goes with it, and changes nothing else: an order to a unit takes the holds queued on that unit if it was the last queued order to it, and a `set_intent` that makes a new intent takes the commands queued for that intent as their own (its limits, its leave to pursue, its withdrawal). It is refused, with nothing changed, when the game is over, the seat's orders are closed, `as_of` is missing or stale ("the queue has changed since it was listed: call queued again") or no entry has the place; and it is refused where another queued entry rests on what would go (such as an order to a force a queued forming order makes): the words name that entry with its place. Each remaining entry is judged again as it was judged when queued, and one that passes now and would fail without the entries taken back is the one named. A preview made before a take back is void after it. Both tools are the session's: nothing in the state, the hash or the saved game changes, and a take back is recorded nowhere but in the transcript. A watcher has neither (decision 0182). The schemas are `queued.schema.json` and `take_back.schema.json`.

**The patrol of submarines in the command tools** (decision 0218, stage 3; agent interface version 48). `set_intent` takes `intent_kind` `patrol` with `hex` and `distance` (no base); `hold` and `release` take `submarine` (the side's boat number) as one more target; `set_limit` forces takes `submarines`, the side's boat numbers, which `command_state` shows in the limit and as `submarines_binding`. `list_forces` gives each boat a `hands` (`staff` under an intent, `commander` by a hold or an order, or `free`), `list_contacts` gives `submarine_reports` and `suspected_waters` (the side's reports and belief only, apart from ship contacts; left out when none), and `propose` and `preview` give `stations`, each boat the staff would station as `{submarine, name, hex, place}`, for a patrol intent (left out otherwise).

**The staff's reading of a draft** (decision 0221, the staff's reading; agent interface version 49). `preview`'s `with_change` gains, where the staff has a proposal for the intent, the proposal's `tree` (the sub-intents it would form, each with its number, parent, kind, words, reason and cautions; the air groups' orders by intent; the search arcs; the decisions to give no order), `would_hand_in` (the orders, commands and decisions to give none it would hand in for the intent) and `reason`, as `propose` gives them for an intent in force. A draft is so read in the shape of a plan. Nothing else in the answer changes.

**Tools of a seat with a staff** (decision 0107, step 3, stage 1, step 1). Every seat of a game opened by `mcp`, `play` or `serve` has a staff (`sim_staff::staffs()`), so these nineteen tools follow the nine: `command_state` (what stands as the coming day will find it: intents, each root by number with the intents beneath it after it, and for each its kind, base, `parent`, `maker` (`commander` or `staff`), `addressee`, `children`, `depth`, limits as set on it and `limits_read_up` (each limit as the staff reads it up the tree, with the intent it is read from and what holds where none is set), for a hold intent its `measure` (days in force, days met, air raids, raids a patrol fought and the base's days of supply, with words), each intent's days-of-supply projection with its first day below the floor, leaves, reserves, plans, commitments, the commands queued, and yesterday's staff decisions with their `why` numbers), `plans` (plans and what each run is doing), `set_intent` (with no `intent` number it takes the side's next free one; `intent_kind` is `keep_supplied`, the default, `hold`, `cover`, `neutralise`, `raid`, `deny`, `strike_ships`, `search_waters`, `stand_at`, `operate_carriers`, `ready_landing` or `build_up` (decision 0141, above); `stand_at` and `operate_carriers` take a `task_force` (one of the side's own, in its numbers) and a `hex` (`[q, r]`, on the map) and no `base`; `floor_days` and `interval_days` are for `keep_supplied` alone; `neutralise` takes a `target` and no `base`, `raid` a `base` and a `target`, `deny` a `hex` (`[q, r]`) and a `distance` (whole hexes) and no `base`, `strike_ships` a `base`; `search_waters` is the staff's and is refused as "Not a root"; a `deny` whose hex is not on the map is refused as "Not on the map"), `withdraw_intent` (it withdraws what stands beneath the intent too), `set_limit` (it works on any intent, a staff-made one too, a limit on an intent with a parent that does not narrow its parent's is refused, and `forces` takes `air_groups` and `land_units`, with `ships`, `task_forces` and `source` optional), `set_leave`, `hold`, `release`, `approve`, `cancel_plan` (each queues one command for the coming day, checked at once by taking it in on a copy of the world after the commands already queued, and answered `queued` or `refused` with the engine's reason in the side's numbers; `clear: true` empties the queue first), `propose {intent}` (what the staff would do: the projection, the runs over 30 days, what binds, what it would hand in; for a hold or a cover intent a `tree` instead: the sub-intents it would form, the air groups each would order with their orders, and the search arc with its threats), `order {intent}` (decision 0159, rule E, agent interface version 26: the plan of one of the commander's intents as the staff hands it in, answer `plan_order`: the mission, the plan and its state, the phases in order with where each stands, what the plan waits for with whether each is met and the day it is expected, the men wanted and to hand, the day it expects to be ashore, the need to know, the staff's tasks under it and a brief in words; read-only; an intent not in force, the staff's own or not the side's is refused as `propose` refuses it), `staff_orders` (what the staff would hand in at the start of the coming day, asked on `World::at_staff_step()`, each decision with its five-part reason), `why {number}` (the reason of one staff decision, whole, and the order or command it is for, with its `chain`: the intents above the one it serves, nearest first, the last the commander's) and `preview` (what a changed `set_intent` or `set_limit` would do, worked on copies of the game and stored nowhere, beside what the staff does as things stand; `approve {"preview": n}` queues exactly the command it showed, and is refused, with why, if the side has queued anything or a day has been resolved since). A game whose scenario names a `trial` file adds two tools to a seat that plays a whole side (decision 0178, agent interface version 29; a game with no such file lists neither): `trial {intent | preview, size}` (an intent of the commander's own, in force or queued, or a preview he was shown, tried in the worlds of a trial for the coming morning with everything he has queued for it; `size` is `small` (the default), `standard` or `full`; answer `trial`: the estimate in a commander's words, with how it went in counts of worlds, what it cost each side as the lowest, the middle and the highest, what the plan needs and has, what the commander's other plans lose, what was assumed of the enemy and what each thing was made from, and where the worlds part; asked at dusk and refused with why at an open day, after the game is over, for an intent that is not his, is the staff's, is withdrawn or has its withdrawal queued, for a preview that is void or not his, and for a size the trial's figures do not name; it takes seconds, twice as long where he has another plan with an end to weigh) and `trials {estimate?}` (answer `trials`: the estimates he was shown, each with the evening it was asked on and what was asked, marked where asked on an earlier evening or before his queue changed; with `estimate` it gives that one again, unchanged). Each changes nothing: no command is queued, no preview is spent, the game's hash is what it was, and the estimates are kept with the session and not in a saved game (rules chapter 9, A seat's trial). Since decision 0181 (agent interface version 31) `trial` takes three more arguments: `compare` (true or false: a second trial, in the same worlds, of the side without the thing tried, the plan as it stands without the draft for a draft of a limit or a change, the side without the order for a new or queued one, the side with it withdrawn on the coming morning for one in force; given beside the first in `beside`, with world for world for the plan as it stands; where none is given it is true for a draft of a limit or a change and for a new or queued order where he has another plan with an end, and false for an order in force and with `dates`), `dates` (`"chosen"` or a list of one or two days after the coming morning, ascending, within the size and the game: the whole order is handed in at the coming morning and at each later date, and the answer is `window`, each date with what came due, the men its take chose, the enemy at the place on its eve as men and cover, the estimate's fields and, for a later date, world for world against the first; refused for an order in force and with `compare` true) and `describe` (true: nothing is played, and the answer `trial_described` says what would be tried, the dates with what is due on each, and the worlds and days of each trial; it is not kept). A refusal names a queued command that names the order the trial would move or leave out (an "after" on it). `trials` names each estimate's `kind`, `trial` or `window` (rules chapter 9, What-ifs from a seat). `hold` and `release` name one of `ship`, `task_force`, `air_group` or `land_unit`, the air group with `setting` `"search_arc"` for its search arc alone and with no `setting` for the whole group; `command_state` also lists the side's `holds`, and a commander's own order to a ship or force in an intent's forces limit, or to an air group an intent may use, holds it too, from that morning (rules chapter 8, Holds and the override). Ships and forces are written in the side's own numbers. Commands take effect at the start of the coming day, before the staff is asked. The staff does nothing for a side until an intent is set: a supply intent needs a forces limit with a source, a hold or cover intent may use the air groups at its base unless a forces limit names others. Leave to prepare is given by default and leave to launch withheld. A session made without staffs (`Session::new` alone) has none of them. A scenario's `enters = N` (decision 0195, rules chapter 1, A unit not yet entered) holds a unit apart from the map until day N, a whole number from 2 to the scenario's `days`. It may be put on a `[[task_force]]` (which enters at its hex with its ships and all aboard them), on a `[[land_unit]]` placed ashore in the hex of a base, and on an `[[air_group]]` placed at a base. The scenario is refused, naming the unit and the key, where: the day is below 2 ("a unit there on day 1 needs no `enters`") or above `days` ("it would never enter"); a `[[ship]]` has it ("a ship enters with its task force"); an air group aboard a ship, or a land unit aboard a task force, has it (each enters with its force); a task force's hex is off the map or land; a land unit placed in a hex with no base, or with men aboard ships, has it; a force carries a land unit that has men ashore or aboard another force; an `[[arrival]]` of aircraft is dated before the day its group enters (the group's own, or its carrier force's); an escort order names a force and its charge that do not enter on one day (or both are there from day 1); or a force held apart is named as another command's `superior` or as a contact's `seen_by`. A held force may have a `superior` of its own, a commander and radio silence: they take effect when it enters. A scenario with no `enters` plays as before, and no daily hash of an existing scenario moves. `run SCENARIO` prints, after its header, a line for each unit held apart: its side, its day, its place and what it brings; and nothing where none is held.

A scenario's `[[supply_line]]` table (decision 0196, rules chapter 2, Stock from off the map) gives a base tons of supply and of fuel each night from off the map. Its keys: `base` (a base of the scenario); `supply_t` and `fuel_t` (each a whole number or a decimal string, 0 where not given, at least one above 0; a TOML float is refused); `first_day` (1 where not given; an aircraft stream begins on day 2, the difference is meant); `last_day` (the game's last where not given); and `side` (the base's side at the start where not given; it may differ from it). The scenario is refused for a base it has not, tons below 0, a line that gives nothing, a first day below 1, a first or last day past `days`, and a last day before the first. A base may have several lines. A line gives on a night in its days when its base is its side's, `StockReceived` is recorded, and nothing given is kept for later. A scenario with no `[[supply_line]]` plays as before, and no daily hash of an existing scenario moves.

`validate BATCH.json MEASURES.toml [--out FILE] [--reference DIR]` judges a batch against a battle's measures file under `data/validation` by the rule of agreement in `docs/step2-spec.md` and writes a markdown report, by default `docs/validation/<battle>-<label>.md`, where the label is the batch's tuning round. A judged measure that agrees with no part of its record from the 25th percentile to the 75th is marked "agrees, at the edge": it still agrees and the battle still passes on it, but the report's head counts it apart from plain agreements and misses, and lists it under "At the edge" with its spread (a miss's spread now carries the 25th and 75th too). The version strings in the tests follow `sim_core::hash::STATE_VERSION` and `sim_core::world::RULES_VERSION`, so they need no edit; the command lists, as a reminder, each file outside `docs/decisions` and `docs/validation` that names another state version. What stays by hand it checks and says so: it runs the test that needs a line in `NOT_IN_THE_FULL_SLICE` (`tests/scenario_07_determinism.rs`) and prints its message when it fails, and lists each file in `tests/` with no `[[test]]` entry in `tests/Cargo.toml`. It ends with, for each group, how many files changed and which (`git status --porcelain`, so against the last commit), the run baselines and the `run_` lines apart (a baseline changed means a game moved; only lines changed means the state or its layout moved and no game did), whether a recorded game's transcript changed or only a save, and a reminder that the recorded games' README takes a "Regenerated after ..." paragraph written by hand. It exits 0 when every step ran and 1 when one failed or the list needs a line, naming the step. `--check` remakes nothing: it runs the tests that compare the generated files and says which group is stale (`run_output_matches_the_golden_files` makes two comparisons and says which failed: the output with its hashes hyphened against the baseline, a game moved, and the day hashes against the pinned line, the state or its layout moved). Run it from the top of the repository, after a rule build and before committing.

**The tools of decision 0138** (who knew what, step 5 of stage 2b). None reads anything a side does not hold except where it is the umpire's, and none changes a game.

- `events SOURCE --report EVENT [--command area|task_force:N|base:N] [--seed N] [--json]` (the umpire's): for a report, known by its event (a sighting's `report_received`, a claim's, a ground count's, a "nothing there"'s `strike_found_nothing`), and each command of its side (or the one named, by the scenario's id), the day and pulse the command first held it and by which road (its own; up, sideways or down, naming the `report_sent` event, its sender and whether it came on time or a pulse late; for a passing down, the passing up behind it), or that it never did and why (each road lost, or late to a command that had ceased to be or a game that had ended). Held or never is read from what each command has heard, pulse by pulse, as the game is played again; the road from the log. With command levels off it says the side held the report when it was made; with them on and no report figures, that every command did.
- `events SOURCE --strike air_group:N --day D --pulse morning|afternoon [--report EVENT] [--seed N] [--json]` (the umpire's): the answer the rules gave a group on the naval strike mission at that pulse's strike decisions, on its command's picture: the group, its command, place, reach, contact age limit, target list, aircraft able to fly, whether it is dark; what it launched, checked against the log's `strike_launched`; and each contact of its command's picture (that picture's number, hex, kind, ships, age, the report it rests on, own or told) with why it was or was not struck: chosen, too old, out of reach, a kind not on the list, another contact came first, served by the groups before it, or the cause that stopped the group (not on the mission, nothing able to fly, dark, no weapon, no position). `--report` says whether that report was held as a contact then, and when it reached the command. It is the strike question of decision 0100 asked of a past pulse, with the strike rule's own functions; a night pulse is refused (no strike is decided in the night).
- `events SOURCE --why EVENT` on a `strike_launched` or a `force_alerted_by_contact`, where reports travel, follows the report it cites only along the road that brought it to the command that decided (the launching group's command at that pulse, or the force), and no longer lists every passing. Elsewhere, and with command levels off or no report figures, it is as before. An order cites no report in the log, so there is nothing to narrow for one.
- **A seat at a command:** `serve ... --seat allied=player --at allied=task_force:2` (or `base:N`, or `area:easier`), `mcp SCENARIO --seat allied --at task_force:2`, and `play --at task_force:2` on the first call (kept in the game file's header). The command is named by the scenario's id. A seat at a task force or a base (command levels on only; refused with them off) is given its command's picture, its own units exactly, numbered from 1 in the seat, every base's public facts, and the events that name its own units only; it has `get_briefing`, `list_forces`, `list_bases`, `list_contacts`, `get_entity`, `measure`, `explain`, `issue_orders` and `end_day`, the command tools are refused, and an order to any unit not its command's is refused "not one of your command's units". The side's staff serves the other commands; an order the seat gives to a unit an intent uses holds it against the staff, as any commander's order does. `area:easier` is decision 0119's easier setting: the side's own picture and its forces exactly. The agent interface is version 16.
- `command_state`, with command levels on, gives `picture` (the area command's contacts with its own numbers, each `own` or told) and `forces_held` (each force and base as the area command holds it, with `as_of` and `current`).
- The command report (`report`) gives `refusals`: staff orders refused because a force was not as the area command held it (decision 0136, 14), other staff orders refused, and commands refused. `batch` gives the same counts for each run and side under `refusals` (batch version 6; `validate` reads versions 5 and 6).
- `export` adds, since decisions 0179, 0180 and 0210, to a raid's `claim_received` data `ground_types` and `air_types` (each `{aircraft_type id, aircraft}`) and `claimed_by` (each `{unit, shot_down, on_ground, hits}`), each only where it is not empty; the log's claim words (`run --events`, `events`) give the types in brackets after the aircraft shot down and after those destroyed on the ground, and end with the clause "claimed by ..." (rules chapter 3, What a raid's claim names). `export` writes replay version 6: for a scenario with command levels on, each command's picture in `steps` and `final` (`pictures`), and each `report_sent` event's listeners with direction, arrival and the day and pulse it arrived. A scenario with command levels off exports as before but for the version. The viewer's "Command picture" selector shows one command's contacts over the truth, and its Reports tab lists the reports sent (`viewer/README.md`).
- `get_briefing` gives, since decision 0183 (agent interface version 32), what the enemy is scored for: in the data, `enemy_objectives` in the objectives part (each of the enemy's objectives with its `kind`, `base`, `closed`, `ship_points`, `points` and, for ships out of action, `horizon_days`; left out where the scenario has no objectives and at a seat at a command, an empty list where the enemy has none), and in the text, after the line of the levels, "The enemy is scored for:" with a line for each. Nothing of the enemy's mission, progress or state.

`python3 table/serve.py SCENARIO --seat allied [--start 1942-08-07] [--island "1=Guadalcanal@1"] [--map FILE] [--directives FILE] [--port 8742]` serves the table, a prototype of the player's interface, at http://127.0.0.1:8742/ (decision 0154). It starts `target/release/sim-cli mcp SCENARIO --seat SIDE`, which must be built, and passes the page's tool calls to it: the page is given one seat's tools and the map's hexes and nothing else. `table/README.md` says what it does and does not do. It has no test; CI runs `check_screen.py` (with `check_watch.py`), which checks the page's text, its own wording and the bridge, while the page as drawn in a browser is still tried by hand. Started with no scenario, `python3 table/serve.py [--port 8742] [--keep DIR] [--hold 50] [--scenarios FILE]` prints the table's address, `http://127.0.0.1:PORT/table/KEY/`, which opens at the new game screen (decision 0185): the scenario from `table/scenarios.json`, the seat (a side, or to watch) and who plays each other side (the engine or an agent). A person against the engine is held on `sim-cli mcp`, a game watched on `serve --watched` as `--watch` holds it, and a person against an agent on `serve --watched` with both seats played, the bridge stepping whenever both are ready and refusing every watcher's request. Each side has a door, `http://127.0.0.1:PORT/seat/KEY`, kept while the bridge runs; with `--keep DIR` each game is kept in `DIR/game-N`. `python3 table/check_screen.py` checks it by script, ports 8780 to 8785, and runs `check_watch.py` after.

**An order's limits, and a limit that binds what it names** (decision 0222, the engine; agent interface version 50, state layout `flagplot-state-v57`, saved game version 25, rules label 31, doctrine `supply-57`). `set_limit` of `forces` takes `none_of`, a list of kinds (`ships`, `air_groups`, `land_units`, `submarines`) of which the staff may use nothing; naming a unit of a kind and listing it is refused ("Named and none of"). It takes `in_place` (true or false): the task forces it names work from where they lie, and a limit naming no task force with it is refused (ruling I). `set_limit` of `forces` or `area` with `cleared` true and no other key but the intent clears the limit; a forces limit with no list, no source and no `none_of` is "use nothing", not cleared. A scenario's `[[command]]` takes the same keys (`none_of = ["air_groups"]`, `in_place = true`, `cleared = true`). `preview` of a `set_intent` takes `limits`, a list of `set_limit` bodies without `intent`, worked with the order as one; its answer adds `limits` and `shown_limits`, and a refusal of one of the batch says which (`of_batch`, `{position, size}`). `approve` of that preview queues the order and its limits (`limits_queued`). A reason gains `limits`, the limits it speaks of, each `{kind, intent}` or `{kind: "reserve", base}`, left out where there are none, in `why`, `staff_orders`, `propose`, `preview`, `run`, a saved game's hand-in and the export's `staff_reason` (`limits`, in words). `command_state` shows a forces limit's `none_of`.
