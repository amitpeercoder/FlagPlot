# Commands

What each command of the workspace does. `CLAUDE.md` lists the commands themselves; this page explains them. It was moved out of `CLAUDE.md` on Nov 12, 2026 to keep that file short.

`serve SCENARIO --seat allied=player --seat japanese=script` holds a game open and takes one JSON request a line on standard input (decision 0050). `mcp SCENARIO --seat allied` serves the same game and tools as a Model Context Protocol server on standard input and output, and `play --game FILE ... TOOL [ARGUMENTS]` makes one call to it and exits, keeping the game as a file of the calls made (decision 0051); `play` alone prints how. The tools' `measure` takes a fifth question, `{"question": "yard", "task_force": "task_force:N"}`, which answers whether a `send_to_yard` order given now would be refused and why, the port and passage, each ship's days of repair, the days away, the day the force would be back and whether that is before the game's last day, or for a force already away its port and day of return (decision 0069). The `air_reach` answer of `measure` also gives the group's `transfer_range_nm`, the farthest base a `rebase` order can name; the briefing's air group line and `get_entity` give `moved_yesterday` (true the day after a move, when the group flew nothing), and the briefing's losses give `air_groups_rebased` and count aircraft written off by a rebase in `written_off` (decision 0091). The tool `list_contacts` also answers `ground_estimates`, the side's estimates of the enemy's men ashore, one for each hex (the men, the day reported and the age in days), in the area if one is given, and left out when the side holds none; the briefing has the same in its `enemy_ashore` part, and in its action part the side's own bombardments, its ships' shell fire and the bombardments of its own bases (decision 0092). `play --export-save FILE` is refused, with a plain message and exit status 1, until the game is over (a saved game holds both sides' orders); `--export-transcript` alone is allowed at any time, as it holds only the seat's own calls (decision 0085). `.mcp.json` starts that server for Claude Code in this folder, on the full slice with the player as the Allied side (decision 0051, added on the designer's word); edit its last arguments for another scenario or seat. For a scenario with objectives, `run` prints the umpire's result after the final state: each side's points by objective with its count (a base's "of N days", ships out of action's "over N days", the horizon), the total, the margin and the outcome, then for `ships_out_of_action` one line for each ship counted with her days at the end, the days she left for a yard with, her days out, her share and her points (decision 0088), and the history note. In a scenario with land units `run` also shows them, and shows nothing of them in one without (decision 0066): a ship line ends with ", N men of land_unit:M aboard" when she carries men, a base a landing formed ends with ", formed in play, on its own side's map only", and after the bases it prints one line for each land unit with its side and either "N men ashore at (q,r)" or "no men ashore", with ", on attack" and ", fatigue N" when the unit is on attack or tired, and an air group lost with its base is shown as "lost with its base" (decision 0090); its events (men embarked and landed, a base formed, a unit divided, men fed, men lost and a unit destroyed) are in the `--events` text, each with its causes. After the final state `run` also prints each side's estimates of the enemy's men ashore, one line for each, "Allied estimate at (q,r): N enemy men ashore, reported day D", and prints none for a side that holds none, so a game with no ground report reads as it did (decision 0092); a bombardment (a ship's fire and the force's), men lost to fire, a ground report and a base found are in the `--events` text with their causes. `run --save FILE` writes a saved game (the scenario's name, the seed, each day's orders and the daily hashes); `replay FILE` runs it again and fails on the first day whose hash differs, and refuses a scenario or data file that has changed; `hash` prints the daily hashes only (decision 0043). `events SCENARIO_OR_SAVE --unit HANDLE [--day N]` is the umpire's question to a finished run: it prints every event that names a ship, task force, air group, base, land unit or contact (`land_unit:N`, the engine's number, as the umpire's tools use) in the text `run --events` prints (a ship's task force's events too, marked `via`), and `events ... --why EVENT` prints one event and its causes down to orders as a tree (decision 0052, item 9). `export SCENARIO_OR_SAVE --out FILE` runs a scenario exactly as `run` does, or replays a saved game as `replay` and `events` do (same refusals: a changed file, a missing `--reference`, `--seed`), and writes it as one replay file for the viewer (decision 0018; a base that changes side is listed in `base_changes`, decision 0090; a bombardment, men lost to fire, a ground report and a base found are events of the file, and the final state lists each side's ground estimates, left out where none is held, decision 0092; version 3 also carries each aircraft type's strike radius, extended reach and search range, and each air group's type number, for the viewer's air layer: `viewer/README.md` has the format); a saved game's replay is titled with the game's file and its scenario, so a recorded game is shown on the map with `export crates/sim-cli/tests/recorded_games/NAME/save.json --out FILE`. It also takes `--seed N` (a scenario only) and `--labels data/map/south_pacific_anchors.csv`. `batch` runs a scenario over many seeds (`--runs N`, default 1000, `--first-seed S`, default 1, `--label TEXT` to record the caller's name for the engine, such as a revision; decision 0057) and writes one summary file of losses per side, per ship and per run, and, for each run, the counts step 2's measures read: hits by ship and weapon, gun and torpedo fire by side, systems out, aircraft lost by group and cause (aircraft written off by a rebase are counted with those worn out, in `worn_out`), aircraft ready at the end of each day, claims by side, attacks, escorts, break-offs and base supply, the gun and torpedo shots each ship fired, and, for each surface fight, who sighted first and the rounds each force was surprised, and every strike launch with its aircraft, hex, whether it found nothing and the task force its raid met (decision 0062; the file is version 5). A run that lost any man has `men_lost`, the men each side lost by cause (`fight`, `unfed`, `lost_with_ship`, `fire` and `surrendered`), and a run with a bombardment has `bombardment_shells`, the shells each side fired; both are left out of a run with none, so the version stays 5 (decision 0092). For the land fight a run also has, each left out where empty: `men_lost_by_day` (`day`, `japanese`, `allied`: the men lost that day by every cause), `airfields_built` (`day`, `base`), `arrivals_delivered` (`day`, `air_group`, `aircraft`) and `ashore_by_day` (`day`, `side`, `q`, `r`, `men`, `supply_t`: the men ashore at the end of each day and the supply of the side's bases in the hex); the batch's header has `daily_supply_t_per_man` when the scenario has ground figures. `validate` has the takes `base_holder`, `men_lost`, `airfield_built_day`, `arrival_day` and `days_of_food` for them (`data/validation/README.md`). It is the umpire's file and shows the truth. `run`, `replay`, `hash`, `events`, `export` and `batch` take `--reference DIR`: the scenario's reference files (ship classes, port sizes, aircraft types, and the search, surface combat, air combat, air upkeep, fatigue, base supply and ground figures) are then read by file name from DIR, in place of where the scenario names them, and one that is not in DIR is an error; the map is read where the scenario names it. `--reference data/reference/step1` runs a scenario on the figures frozen at the end of step 1, which the hand-calculation tests use. A saved game or a batch made with it records DIR's files and their hashes as its inputs, and `replay` and `events` on that game need the same `--reference` and the same files; without it they refuse, saying the scenario now names different data files. `serve`, `mcp` and `play` do not take it. Open `viewer/index.html` in a browser and pick the file. `node viewer/check.js viewer/replays/*.json` checks replays against the page's own rebuild.

`time --machine TEXT` measures what a day costs, outside the game (decision 0100, 11 to 13): one day of the full slice early (day 2 from day 1) and late (day 13 from day 12), the same day with every question of both sides asked at every moment of it and the asking alone once before the day, a copy of the world (the slice at days 1 and 12, the soak at day 150) with and without its event log (the event log is timed alone and the copy without it reported as the difference), and `--games` (100) games of `--days` (30) from the start of the soak and from its day 150. A copy keeps its seed, so those games are one game played a hundred times: the cost is what a trial of that size pays. Each workload is a spread, min, median and max, over `--repeats` (20) runs (the games one run each), in a release build (a debug build says so), and the report ends with the totals that matter. `--slice`, `--soak`, `--early-day`, `--late-day`, `--soak-late-day` and `--reference` change the inputs. It is the one place in the workspace that reads the clock, in one function exempted by name from the lint; nothing it measures reaches a result, and a scenario run before and after it gives the same events and hashes.

A saved game is version 2 since decision 0100: it also records `state_version`, the version string of the state hash's layout, and `rules_version`, the rules label (`sim_core::world::RULES_VERSION`, 5 since decision 0106). `replay`, `events`, `export` and `play --export-save` read a saved game through one reader, which refuses, before anything runs, a saved game of version 1 ("saved before saved games recorded the rules they were played under ... it is not converted, so play it again") and one whose state layout or rules label differs from the engine's, naming both. The recorded games were remade in version 2; their transcripts did not change.

`run SCENARIO` prints each land unit's line with its men ashore and hex, then ", on attack" where the unit is not on defend, ", fatigue N" where its fatigue is above 0 and, since decision 0106, ", fieldworks N" where its fieldworks are above 0; a unit that has dug none has the line it had. `export` writes the final state's land units with `fieldworks` (decision 0106), left out when 0 so that a file made where nobody digs is as it was, as the skills are left out when all are 2 (the rulebook's chapter 7, What a side sees); the events `fieldworks_changed` and `defences_worn` are in its event list. The viewer rebuilds the fieldworks from them (`viewer/README.md`). `events` lists the new events of a unit or a base as it lists any other, and `--why` follows their causes.

The tools' `measure` takes a sixth question, `{"question": "choices", "unit": "air_group:N" | "task_force:N" | "land_unit:N"}`, which answers, for one of the side's own units, every choice the rules would make for it now from what the side holds (decision 0100): the strike, aircraft able to fly, base strike, fighter split, escort, landing, rest, alert, ready, break-off, stragglers, head home, reroute, halt, steam on, back to defend, `attack_spent` (what a spent attacker does: hold or fall back) and the land unit's day, each with the question's parameters as asked and the answer. It is not a forecast, and the five choices made at the point of contact are not asked. A unit the side does not hold answers "not known".

The map tool also has `locate --lat --lon`, `path --from q,r --to q,r`, `sides --hex q,r` (a hex's closed sides and neighbours), `water --lat --lon` (why a position's hex has the water it has) and `generate`, which rebuilds `data/map/south_pacific.csv` from the Natural Earth files under `references/` (the exact command is in the file's header). `generate --anchors data/map/south_pacific_anchors.csv` applies the listed anchorages (decision 0017, decision 6); without it hexes keep their largest body of water. `render` draws `#` land, `+` coast, `%` coast with a closed side toward water and `.` sea, each row labelled with its r and the q of its first hex.

`oob-derive` derives ship classes for a list of real ships from `data/oob` (decision 0020). A ship list that generates class files has a `[class_ids]` table giving each class id and the ships that have it (decision 0077): the tool makes one row for each pinned id, in id order, never merges two, and refuses ships pinned to one id whose figures differ, a ship with no id, a pinned ship not in the list, and an id or ship pinned twice; a row of a class with a twin of equal figures is named with its ships in brackets. A ship list may name working assumptions (unknown radar means none, decision 0019; main-gun ammunition not limiting, decision 0023; surface weapons not modelled, decision 0029), may ask for the air figures and may list aircraft types to derive, and the rules file names every exception. With any problem it writes nothing and lists every problem; `--check` only reports; `--facts DIR` reads another facts directory. A list may also have an `[experience]` table (and no class ships) that derives each listed ship's experience value from four yes or no questions and writes `ship_experience_*.ships.csv` (decision 0064, "As built (the derivation)"); a value that rests on a navy's statement with no second source is marked `provisional`. An answer may take its period from the row's own dates and may use a force's statement with `named_by` rows. The rules file's `[fire_rate]` block (decision 0070) names the cases from `engagement_outcomes.csv` and `engagement_events.csv` whose median is the achieved rate of each kind of battery; a class's `gun_rounds_per_min` is the lesser of its sourced rate and that, and the header of a class file that derives surface weapons has an "Achieved rates of fire" section after the exceptions (a list with no surface weapons modelled has none). A run and `--check` print, after the files, the rows of the listed ships that no question read; they are not written to the generated file, so a new row does not make it stale. The rules file's `[search_radius]` block (decision 0075) gives each aircraft type a search range of its own, a third of its range in the scouting condition rounded down, with exceptions read for that alone; a type whose range it cannot settle keeps its strike radius, and a run and `--check` list it as not settled.

`validate BATCH.json MEASURES.toml [--out FILE] [--reference DIR]` judges a batch against a battle's measures file under `data/validation` by the rule of agreement in `docs/step2-spec.md` and writes a markdown report, by default `docs/validation/<battle>-<label>.md`, where the label is the batch's tuning round. It takes each measure's number from every run by the measure's `take` (`data/validation/README.md`), in whole numbers only (`shots_in_hundreds` and `shots` take either a `side`'s shots or the summed shots of a list of `ships`, never both; `shots` counts whole shells, or tens with `unit = "tens"`, summed and divided before it is rounded down once, decision 0084): a percentile is the value at place ceil(p x n / 100) of the kept runs, sorted; the Allied margin is ordered by its exact decimal value. A judged measure that agrees with no part of its record from the 25th percentile to the 75th is marked "agrees, at the edge": it still agrees and the battle still passes on it, but the report's head counts it apart from plain agreements and misses, and lists it under "At the edge" with its spread (a miss's spread now carries the 25th and 75th too). The console line reads `judged N, agree A, at the edge E, miss M`. It refuses a batch with no label, a label that is not letters, digits, dot, dash or underscore, a batch that is not version 5, one made with another state hash layout, one whose scenario or data files have changed (give the same `--reference` the batch was made with), measures of another scenario, and a measure it cannot take. Since version 4 it has two takes for the fights' sighting record, `fights_sighted_first` (night fights whose first sighter is one of a list of `allied`, `japanese`, `both`, `neither`) and `rounds_surprised` (the rounds named task forces were surprised in night fights). Since version 5 it has `aircraft_taking_part`: the aircraft launched in ship strikes whose raid met a force of named task forces, with the escorts that went with them if asked. It will not write over a report of the same name unless the bytes are the same. It ends with success whenever it wrote its report, whatever the verdicts. `validate MEASURES.toml [--out FILE]` is for a measures file with no scenario (not built): every measure is reported as not run. No file under `data/validation` is in that state since Cape Esperance's check (decision 0072, "As built (the check)"). It is the umpire's tool; nothing that plays the game uses it.

`validate --passages data/validation/passages.toml --label TEXT [--map CSV] [--places CSV] [--out FILE]` works each ship passage of the file as one calculation, not runs, and reports it beside the record; no passage is judged. A passage's ends are rows of `data/oob/place_positions.csv` (`from_row`, `to_row`; `--places` names another file) or positions (`from_lat`, `from_lon`, `to_lat`, `to_lon`, decimal strings); each is put in a hex in whole-number arithmetic by the projection of decision 0017, and a place is at the centre of its hex. The charged miles are `Map::sea_charged_nm` (decision 0058) on the map (`--map`, default `data/map/south_pacific.csv`), less `to_short_by_nm`; the minutes are those miles at `speed_kn` with `speed_changes` (minutes from the start of the run), rounded up to the minute the miles are reached. The report is `docs/validation/passages-<label>.md` unless `--out` says otherwise; the label rule and the refusal to write over a different report are those of the battle reports, and a row id that is not in the places file, a row with no position, a row of another place than the one named, or a passage with both a row and a position are refusals naming the passage. A run whose end is land or off the map, or with no sea route, is reported as not worked and the others are still reported. It is the umpire's tool; nothing that plays the game uses it.

`sh scripts/decisions-index.sh` writes the table of `docs/decisions/README.md` from the records, one row for each in the order of the file names: the number and the `Summary:` and `Standing:` lines of the record's header (title, `Status:`, `Summary:`, `Standing:`, each a paragraph of its own, at lines 1, 3, 5 and 7). It writes only between the README's two marker lines and keeps the prose around them; a record without the header is named and nothing is written. `--check` writes nothing and fails, with the difference, when the committed table is not what the records give; CI runs it on every commit, documents alone included (decision 0108, item 9). It needs only `sh` and `awk`, and is run from the top of the repository.

`sh scripts/compare-scenarios.sh [--against REV] [--live-only] [--jobs N]` compares every scenario's run with the previous build (decision 0108, item 5), REV, by default the commit the branch starts from (`git merge-base HEAD origin/main`). It runs each file in `data/scenarios` with `run --events` (the soak without `--events`) on the live figures and compares it with the run baseline committed at REV, and runs each file in `data/scenarios/step2-frozen`, and each file in `data/scenarios` without a frozen copy, with `--reference data/reference/step1`, as the hand-calculation tests run them, on this tree and on REV's own build of REV's own files. The hash is cut from each day's line on both sides first, so a change to what is hashed alone shows nothing. It names each run that then differs, with the first line that differs on each side, and each run only one side has, ends with a count, and exits 1 when anything differs. REV is checked out (as a git worktree) and built once in a cache folder, `$TMPDIR/flagplot-compare` or `FLAGPLOT_COMPARE_CACHE`, and reused; remove it with `git worktree remove` to free the space. `--live-only` skips the frozen figures and builds nothing but this tree; `--jobs` (8) is the runs made at a time. It writes nothing in the repository. Run it after a change and before remaking the generated files: with the baselines remade, the live part still compares with REV's.
