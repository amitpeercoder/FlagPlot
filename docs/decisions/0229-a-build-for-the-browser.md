# 0229: A build of the game for the browser

Status: a plan by the architect, written on Nov 24, 2026, at the designer's request of that day, after a talk on how the game reaches other people. The sequence recommended there was: a browser build now, for playtesters, shared by a link, with no install and no server; later a desktop program for a store, reusing the same page and the same core; a hosted server only if the game is ever played by more than one person. This record plans the first of the three and keeps the second cheap. It adds no rule and changes none. It is to be read by a reviewer who has not seen it written before anything is built.

Summary: The table's page played in a browser with no bridge and no server: the game compiled to WebAssembly and held in a worker of the page, answering the same seat tools `sim-cli mcp` answers; the data it plays on packed at build time by `sim-data`; the kept game a file of the seat's own calls in the browser's storage; and a check in CI that the browser's build gives, call for call and day for day, what the native build gives. Seven stages, none with a hand calculation.

Standing: Planned on Nov 24, 2026; amended on review the same day (What the review changed). Stage 1 is built (pull request 730); stage 2 is built (pull request 732), with the two tests the architect's rulings on it asked; stage 3 is built on pull request 733 and waits for the change to its check the architect's rulings on it ask; stages 4 to 7 are not built. Needs review: who playtests and whether the link is public, turning on the host, a new seed for each game, the marks for speed, what a playtester is told of the build, and sharing the packed data (Questions for the designer). The wording of two of `CLAUDE.md`'s "Always" rules was accepted by the designer on Nov 24, 2026 (question 7).

## Why it is a record

A new crate, a new target, a dependency of the workspace, a second program that holds a world, and a second way for the page to reach the game are choices no spec made. Three of the rules that fail silently bear on it: only `sim-data` reads simulation data files, anything that plays is given a seat's view and nothing else, and the same start, orders and seed give the same state hash on any machine. A browser is a new machine, with a 32-bit address space, and the whole world sits inside it.

## What is so today

Read from the code on Nov 24, 2026.

1. **The table is one page and a bridge.** `table/index.html` (one file, no build step) talks to `table/serve.py` by HTTP on the machine it runs on. For a person against the engine the bridge starts `sim-cli mcp SCENARIO --seat SIDE` and passes the page's calls to it one at a time. A game begun from the new game screen is named to it by an absolute path (`os.path.join(ROOT, ..)` in `serve.py`). It passes no seed, so every game of a scenario is played on the scenario's own seed.
2. **What the page asks the bridge.** A tool call (`/call`, answered `{"ok": the answer}` or `{"refused": the words}`); the seat's tool names (`/tools`); what the game is (`/config`: the seat, the date of day 1, the islands, the seat's directives); the chart (`/map`, `/frame`, `/coast`, `/names`); the new game screen (`/scenarios`, `/begin`, `/new`, `/restart`); and, for a watched game or a game against an agent, `/standing`, `/step`, `/agent` and `/seat_calls`. The page keeps small things in the browser's `localStorage` (what is ticked, which directives were read).
3. **The mapping from a tool's answer to `/call`'s** is in the bridge (`Game.call` in `serve.py`): the text of an answer is read as JSON and given as `ok`; text that is not JSON is given as `{"text": ..}`; an answer marked an error is given as `refused`. `sim-cli mcp` gives `get_briefing` as text unless asked for data (`Server::call_tool` in `crates/sim-cli/src/mcp.rs`).
4. **The server of a seat is in the program, not the library.** `mcp.rs`, `staff_tools.rs` and `play.rs` are modules of `sim-cli`'s `main.rs`. The library (`crates/sim-cli/src/lib.rs`) holds `game` (opening a game), `save`, `seat_trial` and `estimates`.
5. **`sim-cli play` already keeps a game as a file of a seat's calls.** It keeps every call the game answered, reads and calls the game refused among them (`play.rs`, `append`). Its first line names the scenario, the seat, where the seat sits, the seed, the doctrine version and a pin (the rules version and the hash of the scenario file and of every data file it names); each later line is one call. A call replays the file first. A file whose pin or doctrine differs from the program's is refused, not converted.
6. **A saved game** (`sim_cli::save`) holds both sides' orders and the hash of each day, and is given to a player only when the game is over (`docs/engineering/truth-and-belief.md`).
7. **Every reader of `sim-data` reads a whole file as text and then parses it.** `Scenario::load_with` reads the scenario and then, by paths joined to its folder and not normalised, the map, the land links and each reference file; twenty-odd `fs::read_to_string` calls in `map.rs`, `reference.rs` and `scenario.rs`, and one `Path::is_file` used only where a reference root is given (the frozen figures). `save::remember` reads each of those files again, as bytes, to hash it.
8. **The page loads two things from the network:** three.js r128 from cdnjs, and three font families from Google Fonts (Barlow Condensed, Courier Prime, Libre Caslon Text).
9. **Nothing in the crates that would go in reads a clock, starts a thread, asks for randomness outside `World::rng`, or uses floating point.** A search of `sim-core`, `sim-data`, `sim-staff`, `sim-trial`, `sim-agent` and `sim-cli`'s library and `mcp.rs` found: `std::sync::Mutex` and `OnceLock` in `sim-core` (`command.rs`, `choices.rs`, `view/seat_view.rs`), which the standard library provides on a target with one thread; file reads in `sim-data` and in `save.rs`, `game.rs` and `estimates.rs`; `include_str!` of the schemas, read when the program is compiled; and `std::env` and the process number only in tests. `Instant` is read only in `timing.rs`, which stays in the program.
10. **The hash does not depend on the width of a pointer.** `StateHasher::count` writes every length as 64 bits, and every number as little-endian bytes. Arithmetic is `i64` with `i128` between (`fixed.rs`).
11. **Speed, natively.** One run, not repeated for this record, of `sim-cli hash data/scenarios/table-rear-bases/07b_slice_submarines.toml` (the 39 days, both staffs) took 7.3 seconds on the Apple silicon Mac this was written on: about 0.19 seconds a day. One run, not a spread, and not a mark.
12. **The repository is public** (`gh repo view`, Nov 24, 2026). Nothing in it is private by being unpublished.
13. **The workspace forbids `unsafe` code** (`unsafe_code = "forbid"` in the workspace's lints), and a crate that takes the workspace's lints cannot change one of them.

## What is built

A folder of static files that is the game: the page, a worker, the game as WebAssembly, the data it plays on, the chart files, the drawing library and the fonts. Opened from any static host, or from a folder served on one's own machine, it plays a person against the engine in the scenarios the table offers, with nothing fetched from anywhere else.

```
table/index.html  --messages-->  worker  --calls-->  sim-web (WebAssembly)
   the page: plays                relays                holds the game, as `sim-cli mcp` does
```

## The rulings

### What is compiled, and where the new code lives

1. **A new crate, `crates/sim-web`: the door of one seat.** It holds one game and answers one seat, as `sim-cli mcp` does. It depends on `sim-cli`'s library, and through it on `sim-core`, `sim-data`, `sim-staff`, `sim-trial` and `sim-agent`. Those six are what is compiled to WebAssembly, with `serde`, `serde_json`, `toml` and `csv`, which are plain Rust. `sim-core` still depends on nothing and reads no file. `map-tool`, `oob-check`, `oob-derive` and the program `sim-cli` (its `validate`, `batch`, `export`, `events`, `time`) are not compiled to it.
2. **It reuses the server of a seat; it does not write a second one.** The server of `mcp.rs` (`Server`, the tools' definitions and the instructions), `staff_tools.rs` and the game file of `play.rs` (its header, its pin and its replay) move into `sim-cli`'s library; `mcp::command`, which reads standard input and calls `crate::serve::open`, stays in the program. They move as `game`, `save` and `seat_trial` moved there under decision 0182. `Server::call_tool` is split so that the part that takes a tool's name and arguments and gives back the text and whether it is a refusal is one public function, which the MCP server and the door both call. The door then does what `Game.call` in the bridge does (item 3 of "What is so today"). Nothing in `sim-agent` changes but the one line of ruling 30.
3. **The door is a plain library first.** `sim-web` is built as both a Rust library and a WebAssembly module. Its type `Door` is ordinary Rust with no binding in it, tested natively by `cargo test --workspace` like any crate; the binding for JavaScript is one small module at its edge, compiled only for the target (`#[cfg(target_arch = "wasm32")]`), each bound function one call of the door. The one door of a module is held there in a `thread_local!` cell; no class is exported. A native program of the crate, `door` (`src/bin/door.rs`), holds a `Door` and answers requests read as lines from standard input, held open for a whole game: it is what the check compares the module with (ruling 29). A desktop shell later calls the same `Door`, natively or as the same module (see "What keeps the desktop program cheap").
4. **The target is `wasm32-unknown-unknown`, the bindings are `wasm-bindgen`.** The target is added to `rust-toolchain.toml` (`targets = [...]`), so every developer and every CI job has it with the pinned toolchain, 1.97.0. `wasm-bindgen` is a dependency of `sim-web` alone, pinned to one exact version (`=x.y.z`, the newest release on the day stage 3 begins), and `wasm-bindgen-cli` is installed at the same version; the build script stops if the two differ. No `wasm-pack`, no bundler, no `npm` packages, no `js-sys` or `web-sys`: the door's arguments and answers are strings, and the pack is bytes (`&[u8]`), which the binding takes without either. A seed crosses as a string of digits, since JavaScript's numbers do not hold every 64-bit one. The module is made with `wasm-bindgen --target web` and loaded by the worker as a module.
5. **Considered and not taken: `wasm32-wasip1` with `sim-cli mcp` itself as the program,** reading its lines from standard input. It would need no binding, no change to `sim-data` and no `unsafe` anywhere. But a program that waits on standard input must block the worker until the page speaks, which in a browser needs a shared buffer and so two headers from the host that a plain static host does not send (GitHub Pages cannot). The build must work from any static folder, so it is not taken.
6. **`unsafe`.** A WebAssembly export is an exported symbol, which the `unsafe_code` lint counts, and the binding macro generates such code. The architect has not compiled it against this workspace's lints (the target is not installed where this was written), so stage 3 finds which of these holds and takes the first that compiles:
   - `sim-web` takes the workspace's lints unchanged (`forbid`).
   - `sim-web` restates the workspace's lints in its own manifest with `unsafe_code = "deny"`, and nothing is allowed.
   - As the second, with `#[allow(unsafe_code)]` on the binding module alone.

   In the second and third the manifest restates the workspace's two clippy lints (`disallowed_types`, `disallowed_methods`) as `deny`, so nothing else is loosened. The lint is settled on the target, since the binding module is not compiled natively: the new CI job runs `cargo clippy --target wasm32-unknown-unknown -p sim-web --lib -- -D warnings` beside the workspace's native clippy, which goes on covering the rest of the crate.

   In every case no `unsafe` is written by hand: a test reads `sim-web`'s source with its comments and the one attribute `allow(unsafe_code)` taken out, and fails on the word. If the second or third holds, the line "No `unsafe`" in `CLAUDE.md` and in `docs/engineering/determinism.md` is amended in that pull request to say: none written by hand anywhere, and `sim-web`'s binding module alone may allow what its binding macro generates. `sim-web` holds no state of the simulation and makes no draw, so nothing the determinism rules protect passes through it.
7. **A profile of its own, `web`,** in the workspace's `Cargo.toml`: `inherits = "release"`, with `overflow-checks = true` written out again and not left to inheritance. A panic on this target ends the module (ruling 27). The stack is set by the build and not left to the linker's default of 1 MB against a native program's 8 MB: `-C link-arg=-zstack-size=8388608` for the target, in the build script's flags. Stage 3 confirms from the linker's own words for the pinned toolchain that the stack lies first in memory, so that running out of it is a trap and never a write over the game's data.

### How the data reaches the build

8. **`sim-data` reads through a source.** A small trait in `sim-data` (`Source`: given a path, the file's text or bytes, or the words of a failure) with two kinds: the disk, which is what every `load` function uses today and goes on using, and a pack, a set of files held in memory by the paths they were asked for. Every reader in `sim-data` takes its text from the source it is handed. `sim-data` is still the only crate that reads a simulation data file, on the disk or from a pack.
9. **A pack is made by `sim-data`, never by hand.** `sim-data` gains a function that loads a scenario from the disk through a source that notes every file asked for, by the path asked, with its bytes: the pack then holds exactly the files that load read, and no list is kept by hand. A new command, `sim-cli pack SCENARIO... --out FILE`, writes the packs of the scenarios named as one file: one JSON object, written by `serde_json`, with `versions` (the rules version, the state version and the doctrine version of the program that made it) and `files` (each path with its text; every file `sim-data` reads is text).
10. **Paths in a pack are the repository's own,** as `sim-cli` run from the top of the repository names them (`data/scenarios/table-boats/01b_midway_submarines.toml`, and `data/scenarios/table-boats/../../map/midway.csv` found by reading `..` as text). So the files a scenario names, and their hashes, are the same strings in the browser as in the native program run from the top of the repository with that relative path, which is how the check runs it. A game begun at the table is named by an absolute path and so pins other strings: a game file does not move between the table and the browser, and none is said to.
11. **The pack is fetched, not compiled in.** One file for a build, holding every game the build offers (the reference files are shared: under 3 MB before the host compresses it). It is fetched by the worker and handed to the module as bytes. It is not compiled into the module, because a file generated before the compiler runs would have to exist for `cargo clippy --workspace` and `cargo test --workspace` on every machine. The module refuses a pack whose three versions are not its own, in one sentence. The versions do not name a build, since a change to a figure alone leaves them as they were; a build is named by what ruling 34 gives it, and a module and a pack are of one build because they lie in one folder that is never changed.
12. **File hashing goes through the source.** `save::remember` and `save::inputs` take the source the scenario was loaded from. Writing and reading a saved game and a transcript are split into the making of the text and the writing of the file, so the door makes the text and never names a file.
13. **The pack is the umpire's.** It holds the scenario files: both sides' starting state and the orders the engine's side is given. The page never fetches it, never reads it and is never handed it. Only the worker fetches it, and the worker does nothing with it but hand it on (rulings 20 to 24).
14. **What is not simulation data is made as files at build time,** by the bridge's own readers, so there is one reader of each: the chart of each map (hexes, frame, coast, names: `read_map`, `read_frame_and_edges` and `load_chart` of `serve.py`, imported by the build script), the list of games (`table/scenarios.json`, cut down to the games the build offers) and the directives. The page fetches the directives of its own seat's side and no other. A map is known to both sides (decision 0154). The simulation reads none of these.

### How the page talks to the game

15. **One seam in the page.** Every request the page makes of the bridge goes through one function in `table/index.html` (today a dozen `fetch` calls). Behind it is one of two doors: the bridge by HTTP, as now, or the worker. The page is the same file in both and does not know which it has, except through `/config`, which says what the door offers. The bridge stays: it is how the table is developed, how agents take a seat and how a game is watched.
16. **The worker's door** is a small script, `web/door.js`, and a worker, `web/worker.js`, that loads the module. `table/index.html` holds the seam and one marked comment line before its own script; under the bridge that line is a comment and the seam finds no door and uses HTTP. The build script writes the site's page as `table/index.html` with that one line made the script tag of `door.js`, and changes nothing else in it: the check compares the two files and allows that line alone to differ. `door.js` is the page's own, and plays; `worker.js` is the umpire's relay. Both lie in `web/`, at the top of the repository, and not in `table/`, which reads nothing of the umpire's (ruling 23). The game runs in the worker so that a day being resolved does not freeze the page. The worker takes one message at a time, so calls are answered in the order sent, which is what the bridge's lock did.
17. **What the door of `sim-web` offers.** These seven are the module's whole door. The binding adds exports of its own that carry no word of the game (`memory`, names beginning `__wbindgen_`, `__wbg_` or `__externref_`, and, as amended by the rulings on pull request 733, the globals `__abort_handler` and `__instance_terminated`); the check allows those and no other name:

    | Function | What it does |
    | --- | --- |
    | `versions` | The rules, state and doctrine versions the module was built with |
    | `begin` | Takes the pack's bytes and a request: the scenario's path, the seat, and a seed (a string of digits) or none. Opens the game. One seat for the life of the module |
    | `tools` | The seat's tools, as `tools/list` gives them |
    | `call` | One tool call: `{"ok": ..}` or `{"refused": ..}`, as `/call` answers |
    | `game_file` | A game file `sim-cli play` reads: its header, and each of the seat's calls the game answered that is not a read, calls the game refused among them (ruling 33) |
    | `resume` | Takes the pack's bytes and a game file, and opens the game by replaying its calls; refuses a file whose pin or doctrine is not the build's, as `sim-cli play` does |
    | `saved_game` | The saved game as `sim-cli play --export-save` writes it; refused until the game is over |

18. **Where each of the bridge's duties goes.**

    | The bridge today | In the browser build |
    | --- | --- |
    | Starts and holds `sim-cli mcp`; restart and new game start another | The worker holds one module for one game; a new game or "begin again" ends that worker and makes a new one, and a worker whose module has ended is never used again |
    | Passes calls one at a time | The worker's queue of messages |
    | Turns a tool's text into `ok` or `refused` | The door, in Rust (ruling 2) |
    | `/tools` | The door's `tools` gives the definitions; `door.js` gives the page their names, as the bridge does |
    | `/config` | Made by `door.js` from the game's entry in the list and what the door offers |
    | `/scenarios`, `/begin`, `/new`, `/restart` | `door.js`: the list is a static file; begin, new and begin again make a worker |
    | `/map`, `/frame`, `/coast`, `/names` | Static files made at build time (ruling 14) |
    | Serves the page | The static host |
    | The key in the address, the check of the content type | Gone: nothing listens, so there is no door for another program to call by mistake |
    | A watched game, an agent's seat, a person against an agent, `seat_mcp.py`, `--keep` | Not in this build. The new game screen offers only what `/config` says the door offers: a person against the engine |

19. **The page's every word of the game is still a seat tool's answer.** The door calls the same function `sim-cli mcp` calls, with the same arguments, and stage 2's statement 4 compares the two in Rust, value for value.

### Truth and belief

20. **The whole world is in the browser, and that changes nothing about who may read it.** Natively the world is in a process on the same machine as the page, and the scenario files are on the player's disk; decision 0185 says of the keys that they are no guard against the person himself. The same is true here: a player who opens the browser's tools can read the pack, as he can read the files today. For a game of one person that is accepted. The rule is about our code: what plays is given a seat's answers and nothing else. It is the reason a game of more than one person needs a server, and why none is planned here.
21. **`sim-web` stands where `sim-cli mcp` stands: it is the umpire's side of a seat's door.** It holds the session, which holds the world. The page is what plays. `docs/engineering/layout.md` says so when the crate lands.
22. **What `sim-web` may name.** Its source opens a game, calls the seat's tools for the one side chosen at `begin`, and asks for the game file and, when the game is over, the saved game. A test reads its source, as `sim-agent`'s and `sim-staff`'s do, and fails on `umpire`, `into_world`, `at_staff_step`, `transcript`, `handed_in`, `watch`, `standing`, `seat_calls`, `state_hash` and `day_hashes` by name. A state hash changes with what a seat cannot see (decision 0085), so the door never gives one while a game is in play; the hashes of the days reach the outside only inside the saved game, when the game is over, as the rule already allows.
23. **What the worker may do.** It fetches the module and the pack, hands the pack to the module, and relays the seven functions of ruling 17 by name. It reads no answer and no pack. Its list of messages is fixed in its source.
24. **What the page may do.** It sends messages to the worker and fetches the static files of ruling 14. It never names the module or the pack. The build's check enforces the three boundaries, on the files that are shipped:
    - the module's exports are the seven of ruling 17, all present, and beside them only the binding's own as ruling 17 names them (read from the module itself in node);
    - `worker.js` names no message but those seven, takes the pack only as `arrayBuffer()`, and contains none of `JSON.parse`, `TextDecoder`, `.text(` and `.json(`, so it has no means to read a pack or an answer;
    - `index.html` and `door.js` contain neither the module's file name nor the pack's, and `door.js` is the only thing that makes a worker.
25. **The game file is the seat's own and may be kept and given at any time.** It holds the seat's calls and nothing of the other side. The saved game holds both sides' orders and is refused until the game is over, in the words `sim-cli play` uses.
26. **One seat for a game.** The module serves the seat named at `begin` and has no way to name another. A page that began the same game again from the other seat would see the other side, exactly as a person who starts the table again as the other side does today; the page does not do it, and nothing in this plan pretends to stop a person who sets out to.
27. **When the engine fails,** the player is told one fixed sentence (decision 0085). On this target a panic ends the module with no words given to JavaScript; the build installs no hook that would print them. The worker answers every later message with the fixed sentence, and the page offers to take the game up again from its game file as it stood before the call that failed (ruling 34). The game file is what a playtester sends with a report: played natively by `sim-cli play`, it fails in the same place with the umpire's words.

### Determinism

28. **The requirement.** For the same scenario, seed and calls, the browser's build gives the same answers and the same hash of every day as the native build. A game file from one plays to the same game in the other.
29. **How it is checked: against the native build, on the same commit, in CI.** No hash is pinned and no number is written by hand: the expected value of every comparison is what the native program gives. The same `Door` is built twice in the `web` profile, as the module and as the native program `door` (ruling 3), so the two differ in the target and in nothing else, debug assertions included (off in both; the ten `debug_assert!`s in the crates that go in are run by the native tests, in the `checked` profile, as now). `web/check.mjs`, run in node on the very files the build ships:
    - plays each game file of `web/games/` through the module and through one `door` held open for the game, the same requests to each, and compares every answer as the string the door gave, byte for byte. Both strings are written by the same `serde_json` call, so nothing is parsed in JavaScript, where a large number would lose its last digits on both sides alike;
    - at the end of each, asks both for the saved game and compares them byte for byte, which compares the hash of every day and the orders both sides handed in;
    - takes a game file half played in the module and continues it in `door`, and the reverse;
    - once, for one short game, has `sim-cli play --export-save` write the saved game of the door's game file, and compares it with the door's.

    `sim-cli play` is used for that last comparison alone: it replays the whole file at every call, which over a game of 39 days is hundreds of days resolved. That the door answers as `sim-cli mcp` does is stage 2's statement 4, natively.

    The game files are: one for each scenario file the build offers (ten today), in which the person's seat calls `get_briefing` and ends each day to the last, so the engine's side, both staffs where the file has them, and every rule that fires in those games are run, the 39 days twice over; and four in which the seat gives orders (statements 6 to 9). `check.mjs` also fails if the files of `web/games/` are not those of the games the list offers a person against the engine. The existing machinery it stands on is the game file and its pin, the saved game's daily hashes and `tests/golden/pinned_hashes.txt` for the native side, which is unchanged.
30. **What threatens it, and what was found.**
    - **Overflow checks.** On in the `web` profile by ruling 7; the check script reads the workspace manifest and stops if the profile lacks the line. An overflow is then a panic in both builds, never a wrapped number in one.
    - **A 32-bit `usize`.** The hash is safe (item 10 of "What is so today"). Two things are not checked by the compiler. A cast `as usize` from a 64-bit value would cut it silently: the uses the architect read (`claims.rs`, `bombardment.rs`, `rearm.rs`, `submarine.rs`, `sim-staff`'s `projection.rs`) cast `u32` and small counts, and `station.rs` uses `usize::try_from(..).unwrap_or(usize::MAX)` on a count of hexes, which is harmless. That reading was not the whole of it: the review named more in `sim-core` (`ground.rs`, `damage.rs`, `surface/fire.rs`, `airstrike`) and in `sim-agent` (`trial.rs`, `explain.rs`, `reporting.rs`, `staffing.rs`, `briefing.rs`), which it judged harmless, and one that is not. In `sim-agent`'s `session.rs`, `take_back` reads `number` by `as_u64` and then `usize::try_from(n).ok()`: for a number of 2 to the 32nd or more that is a value natively and nothing in the browser, so the words of the refusal would differ. No honest call sends such a number, but the two builds must answer alike, so stage 3 reads it through `u32` in both, which changes the native words for such a number and nothing else. Stage 3 reads every `as usize` and every `usize::try_from` in the six crates and lists them in its "As built". And a product of two lengths that fits 64 bits and not 32 would panic in the browser alone, which the check would show as a failure, not as a wrong game.
    - **Unstable sorts.** The standard library's unstable sort chooses its method by the size of what it sorts, and the size of anything holding a pointer or a length differs on a 32-bit target. Two things that compare equal and are not the same could then be left in a different order. Today every unstable sort in `sim-core`, `sim-staff` and `sim-trial` (nine outside tests) and in `sim-agent` (eight: `staffing.rs`, `reporting.rs`, `common.rs`) is a plain `sort_unstable()` on whole values, where equal means the same, and there is no `sort_unstable_by`, `sort_unstable_by_key` or `select_nth_unstable` in any of the crates that go in. Stage 3 adds those to the workspace's disallowed methods in `clippy.toml`, with this reason, so that one cannot be added later. Whether clippy takes the path of a method of a slice there is not known to the architect; if it does not, a test that reads the six crates' sources and fails on the three names does the same work.
    - **Time, threads, files, randomness.** None is used by what goes in (item 9). File reads go through the pack. The seed is the only number that comes from outside, as `--seed` does natively.
    - **The stack and memory.** The stack is set to a native program's 8 MB (ruling 7), and the target's memory stops at 4 GB. Running out of either ends the module; with the stack first in memory, as stage 3 confirms, it cannot change a result. A recursion deep enough to end the browser's build and not the native one would show in the check as a failure. Stage 6 measures the most memory a game of the 39 days takes.
    - **Tools that rewrite the module.** None is run on it in this plan. If one is added later to make it smaller, the check runs on the file it wrote, since the check always runs on what is shipped.
31. **Held in reserve.** If the check ever finds a difference, the tool to find where is the whole test suite compiled for a 32-bit WebAssembly target and run outside a browser. It is not built now: it would about double the time CI spends.

### Kept games, and which scenarios are offered

32. **A kept game is its game file,** in the browser's IndexedDB, one record a game: the file's text, and beside it what the page needs to list it (the scenario's name, the seat, the day reached, the build's name and folder, when it was last kept). The time of day on that record is the page's own, read in JavaScript, and reaches no part of the game. `localStorage` goes on holding what it holds today. Storage is behind one small object in `door.js` (list, read, write, remove), so a desktop shell can put files on a disk behind the same four words.
33. **It is kept as the game is played.** `sim-cli play` keeps every answered call; the door leaves the reads out, since the page reads many times at every stop and a file with them would be many times longer and slower to take up. A read is a call of one of `sim_agent::WATCHER_TOOLS` (seventeen tools, `record.rs`), which the session's own words say change neither the game, the queues nor what a preview or a trial is numbered; every other answered call is kept, a call the game refused among them, as `play` keeps it. Such a file is still one `sim-cli play` reads. Statement 5 holds the claim it rests on: a game replayed with its reads left out answers every later call as the game did. After every call that is kept, the worker asks for the game file and the page keeps it. A game is taken up again by `resume`, which replays its calls. At the native speed of item 11 and a guess of two to three times slower in a browser, a game at its 39th day takes on the order of 15 to 25 seconds to take up; stage 6 measures it and the page says that it is being laid out again while it waits.
34. **A game belongs to the build it was begun on.** A change to a rule, a figure, a scenario or the doctrine changes the pin, and the game is refused, not converted, as natively. So that a new build does not end the games playtesters have in hand, each build is published in a folder of its own and is never changed. A build is named by the date it was cut, the commit it was cut from and the hash of its pack (the state hash's FNV-1a over the pack's bytes, as files are hashed), written by the build script into `build.json` in the folder, which the page reads; the address given to playtesters opens the newest. A kept game opens in its own build's folder, which the page finds from the folder on the record (the folders are on one origin, so they share the storage). On GitHub Pages that origin is shared with every other site of the same account, so the database and every key the page keeps are named `flagplot`, as the `localStorage` keys already are, and what the page keeps for one game (what is ticked, why the clock stopped, which directives were read) is keyed by the kept game's own name, not by scenario and seat alone. Old builds are removed by hand when no one has a game on them.
35. **The player can take the game file out and put one in,** as a file he saves and a file he chooses. It is how a report of a fault is sent.
36. **The scenarios offered are the table's:** every game of `table/scenarios.json` in which a person plays a side against the engine. Today that is Midway, the Coral Sea, the Eastern Solomons over one day and over five, and the 39 days of Guadalcanal, each from either seat. Nothing is offered that the table does not offer, and no scenario is made for the browser.
37. **The seed is the scenario's,** as at the table today. `begin` takes a seed so that this can change without a new build of the door; whether it should is the designer's (question 3).

### Speed

38. **How it is measured.** `sim-cli time` reads the clock inside the program, which this target does not have. In the browser the clock is read by the worker, with `performance.now()` round a call of the door, outside the game as decision 0100 requires. A page of the build, `time.html`, not linked from the game, runs fixed workloads through the door and reports each as a spread over repeated runs, naming the machine and the browser: `end_day` on the 39 days early (day 2 from day 1) and late (day 13 from day 12), as `sim-cli time` has them; a quiet week by `run`; a dry run on Midway at each size the tool offers; taking up a game at day 20 and at day 39; opening a game from a cold page; and the module's memory at the end of the 39 days. `check.mjs` runs the same workloads in node and prints them beside the native program's on the same machine, as a ratio. No number fails CI: a shared CI machine's time is not a measurement.
39. **The marks are the designer's to accept** (`docs/step3-spec.md`, "Speed": inside times the designer accepts). The architect proposes, for the machine and browsers named in stage 6: a day of the 39 days resolved in 2 seconds or less at the middle of the spread, late in the campaign; a game at day 39 taken up in 60 seconds or less; a game opened from a cold page in 10 seconds or less on a home connection. No mark is proposed for a dry run until its figures are seen beside the native ones. Stage 6 reports the figures against these and the designer accepts them or sets others (question 4). If a day misses its mark, the first thing to look at is what the native build spends its time on, since the browser runs the same code.

### What the page loads

40. **Nothing from another site.** three.js r128 and the three font families are kept in the repository under `table/vendor/`, with a file beside them, `vendor.toml` (TOML and not Markdown, because the build and the check read it), that gives, for each, its version, where it was taken from, its SHA-256 and its licence, and the licence texts themselves. The page loads them by paths of its own; the bridge serves the folder, so the table at a desk no longer needs the network either. A playtester's browser then calls no one but the host.
41. **The licence check owed before the link is given to anyone** is a file in the build, `NOTICE`, made by the build script, that lists every file shipped with where it came from and under what terms, and stage 6 is not done until the architect has read it. What it must settle:
    - **three.js:** MIT; the notice and the licence text go with it.
    - **The fonts:** each family's licence is read from the family's own licence file when it is brought in, not assumed. They are believed to be under the SIL Open Font License, which allows them to be shipped with the licence text beside them; if one is not, it is replaced before anything is shared.
    - **The coast** (`table/chart/*_coast.json`) is cut from Natural Earth, which is in the public domain (`table/README.md`); the names are from `data/oob/place_positions.csv` rows.
    - **The maps** (`data/map/*.csv`) are generated by `map-tool` from Natural Earth.
    - **The reference figures and scenarios** are the project's own, derived or estimated by its written rules from facts it cites, or marked placeholders. Nothing from `data/oob`, from `references/` or from another game's database is in a pack, because the simulation reads none of them and a pack holds only what a load read; the check script reads each path in the pack with its `..` parts worked out and fails if one is outside `data/scenarios`, `data/map` and `data/reference`.
    - **The directives** are written by hand in the game's own words.

### Hosting, and what stays private

42. **The criteria.** A host of static files over HTTPS that sends `.wasm` as `application/wasm`; no code on the server; no header the build depends on; folders that can be kept unchanged beside newer ones; no cost; and nothing that counts or follows the players. The build must also play from a plain folder served on one's own machine, which is how it is checked before it is published.
43. **The architect's choice, if the link may be public: GitHub Pages from this repository,** published from a branch of its own (`gh-pages`), one folder a build, by a workflow started by hand, in a file of its own with leave to write the repository's contents; `ci.yml` keeps its leave to read only. The repository is public already, so the host needs no new account, no secret and no payment, and a public page shows nothing the repository does not. Nobody pushes to `main` and that does not change: the workflow writes only that branch. If the link must be closed to all but named people, Pages cannot do it for this repository, and the choice is a host that can put a sign-in in front of static files; the build is the same folder either way. Which it is, and turning the host on, are the designer's (questions 1 and 2).
44. **What is published** is the build's folder and nothing else. **What is not:** the umpire's tools and what they write (the viewer, replays, saves of games in play, batch files, validation reports), `data/oob`, `references/`, the bridge, and anything of an agent's. The page sends nothing anywhere: no count of visits, no report of a fault, no address. A playtester's games are in his own browser and nowhere else. The designer's email address is in no file of the build.
45. **The build says what it is.** One line on the new game screen gives the build's name (ruling 34). What else a playtester is told (that it is an unfinished game with placeholder figures, and how to send a game file) is the designer's words to write or approve (question 5); the table's rule stands that no caption explains a rule.

### CI

46. **One new job, "Web build and its check",** beside the others, run whenever the full checks run, which is every change that is not Markdown alone (`.github/scripts/needs-checks.sh`); the required check waits for it as it waits for the rest. It installs the pinned toolchain with the target, installs `wasm-bindgen-cli` at the pinned version (built from source by `cargo install --locked`, kept in the job's cache under the version, so it is built once for each version and no program is downloaded ready made), runs clippy on `sim-web` for the target (ruling 6), builds `door` and `sim-cli` natively in the `web` profile, runs `sh scripts/web/build.sh`, then `node web/check.mjs`. The job is added to the `needs` of the required check and to the list of results it loops over, with the same rule: success, or skipped where only documents changed. It runs on every such change because any change in `sim-core`, a staff or a data file can break the equality of ruling 28, and a difference found a week later is hard to trace.
47. **It reads no Markdown.** The check reads `Cargo.toml`, `clippy.toml`, the shipped files and the game files. A pull request of documents alone runs none of it, as it runs none of the other checks.
48. **Not in CI:** a real browser. Node proves the module, the pack, the worker's script as text and the boundaries of ruling 24; it does not prove that the page draws. Each stage that changes the page is checked by hand in the browsers named in its "done", and `table/check_screen.py`, which CI does not run, goes on checking the page against the bridge when a developer runs it. A browser driven by script in CI is left out for its weight and can be added if the page breaks unseen.
49. **Publishing is not part of the checks.** The workflow that publishes is started by hand, builds from a commit of `main` whose checks passed, and runs `check.mjs` on what it built before it writes anything.

## What keeps the desktop program cheap

1. The page is one file with one seam, and reaches the game, the storage and its static files through `door.js` alone. A shell that shows a page (Tauri, for one) loads the same folder.
2. Every address in the build is relative, and nothing depends on a header, a service worker or a particular host.
3. `Door` is plain Rust. A desktop program can run the same module in its own page with no change at all, which is the cheapest first step, or call `Door` natively behind a third door in `door.js` if the browser's speed is not enough.
4. Kept games are files in the game's own format behind four words. On a desk they become files on the disk, and a game moves between the browser and the desktop program by its game file, provided the two are of one build.
5. Nothing in this plan signs, packages or updates a program, and no choice here closes one.

## What it leaves out

- A desktop program and a store. A server, accounts, and any game of more than one person.
- Agents, a watched game, a person against an agent, the MCP door: they stay with the bridge.
- The umpire's tools: the viewer, replays, `events`, `validate`.
- A phone or a touch screen. The page is laid out for a keyboard and a pointer; under 1,100 wide it uses its drawer and no more is done.
- Playing with no connection after a first visit (an installed page). The build plays from a folder; nothing caches it for the player.
- Converting a kept game to a newer build. A game is finished on the build it began on.
- A dry run made faster, or one that can be stopped. Midway, the Coral Sea and the five days name a trial's figures, so the build offers the dry run as the table does. It is one call of the tool `trial`, played to its end inside the call as natively; in the worker it leaves the page live, and it ends early only if the game is closed. Stage 6 measures it. More than one thread is not used: in a browser it needs the headers ruling 5 turned down.
- A real browser in CI (ruling 48), and the whole test suite on the 32-bit target (ruling 31).
- The map from a seat's tools, and a list of the islands from a seat's tools: both open since decision 0154 and not settled here. The build makes them as files, as the bridge does.
- Counting players or collecting their reports. A playtester sends a game file himself.
- Any change to a rule, a figure, a scenario or a tool of the seat's.

## What it costs

- A crate, a target, and the first dependency of the workspace that is not a reader of data: `wasm-bindgen`, with its macro's own dependencies, and a tool, `wasm-bindgen-cli`, that must match it. Node is already used in CI by the viewer's check; Python is already what the bridge is written in.
- Perhaps the first allowance against `unsafe` in the workspace, for generated code in one module (ruling 6).
- A job in CI on every change that is not documents alone: a build of the module, a native build and fourteen games played twice, the 39 days among them three times. Each game is played once in the module and once in a `door` held open, so the playing is a minute or two and the builds are most of it. A guess of five to eight minutes beside the other jobs, not after them, and longer the first time a version of the binding tool is built. From the day it lands, a change to the simulation that the browser's build plays differently does not merge.
- A refactor of `sim-data`'s readers and of `sim-cli`'s library that touches many lines and changes no behaviour (stages 1 and 2).
- About 1 MB of other people's files kept in the repository (`table/vendor/`), and a branch that grows by a few megabytes with every build published.
- One more thing the table's page must not break: its seam. The bridge's check and the browser's check both run on it.
- A playtester's game ends with its build unless the build is kept, so builds are kept, by hand.
- These lines become untrue and are changed in the stage that makes them so: in `CLAUDE.md`, "Only `sim-data` reads simulation data files" stays true and gains "from the disk or from a pack", and "No `unsafe`" may gain ruling 6's exception (both are "Always" rules, and their new words are question 7); the layout table gains `crates/sim-web` and `web/`, the second with the line that `worker.js` and the check are the umpire's and `door.js` the page's; `docs/engineering/truth-and-belief.md` gains the page and the pack beside the table and the umpire's files; `table/README.md` loses "The page loads its drawing library and its fonts from the network".

## What the review changed
